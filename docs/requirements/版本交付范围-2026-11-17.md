# WebGuide AI 版本交付范围

更新于 2026-11-22。GitHub 和 Figma 的预设原型已积累实测记录。下一轮验证在用户直接提出目标时，同一套观察和引导机制能否在两个网站上工作。[浏览器导航原型](../design/WebGuideAI-浏览器导航原型.md) · [导航 Harness 设计](../design/WebGuideAI-导航-Harness-设计.md)

## 当前开发顺序

| 顺序 | 做什么 | 怎么看跑通了 |
| --- | --- | --- |
| 1 | 从通用组件出发，设计用户目标、模型按需观察和视觉指引组成的循环。 | 用户用自然语言说出目标，模型能根据页面证据选择高亮，缺少线索时可以补看。 |
| 2 | 用不同网站上的新任务验证。 | 在 Figma 找导出入口，再挑一个原型里没有的 GitHub 任务，检查能否指到实际控件、跟上页面变化，并在到达目标时收起提示。 |
| 3 | 验证引导经验能否复用。 | 比较有经验和无经验的引导结果、错误指引、调用次数与等待时间。 |

实时导航复用已有的通用浏览器组件。固定路线、协作练习和文件核对保留在旧版本。跑通首轮原型再排完整协作、公共经验库和作者工具。GitHub 的 Fork 提示用来验证 AI 如何解释卡点、继续指路。完整的 Fork 贡献流程可单独安排。

## 1. 原 GitHub 协作场景草案

最初按[整体 SRS v0.2](WebGuideAI-SRS-v0.2.md)安排 GitHub 小组协作入门作为首个交付，来由见[场景调整记录](首场景调整-GitHub协作-2026-11-17.md)。现把这个完整流程作为后续场景，下面保留它的范围和完成条件，供协作练习与专项核对使用。

具体路径、结果判定和 SC02-AC01–SC02-AC14 见 [GitHub 协作首场景规格 v0.1](GitHub协作首场景规格-v0.1.md)。

| 项目 | 范围与限制 |
| --- | --- |
| 用户任务 | 帮助不熟悉 GitHub 协作的成员理解 Issue／PR／Project；首段草案为认领 Issue、创建独立工作分支、修改指定文档并发起可评审 PR |
| 运行基线 | 桌面 Edge，英文 GitHub 页面，中文引导与答疑；页面翻译及其他语言组合单独验证 |
| 目标参数 | 目标仓库、Issue、当前成员、指定文档及基准／来源分支；创建后关联实际 PR。参数确认与身份关联规则在新场景规格中定义 |
| 核心能力 | 页面内可视高亮、规则验证、当前步骤 AI 解释答疑、偏离／阻塞处理、同一浏览器会话内暂停继续与最简反馈 |
| 结果核对 | 核对任务对象、实际认领、文档修改、提交与实际 PR 的关联。Open 非 Draft 且必要证据齐全时显示提交已验证；交接提示按评审与 CI 的实际状态呈现。Draft、关闭及合并分别显示；详细条件见 SC02 第 4 节 |
| 教程准备 | 项目维护者提供可维护的 GitHub 协作教程；首版仍不要求完整作者平台 |
| 恢复边界 | 同一浏览器会话，恢复时重查；浏览器重启后提示重新开始，不承诺跨设备恢复 |
| 建议的切片边界 | 已登录且已获仓库写权限，在浏览器中完成简单文档协作；评审合并可另成角色段落。Git 命令行、复杂冲突、Fork 贡献、完整看板管理和教程作者平台随后安排 |

原方案覆盖 FR01–FR10 和 FR18 的最简反馈。本机模拟练习已跑通，真实 GitHub 的 SC02 验收待执行。

## 2. 教程方案的后续候选

录制示范、文档生成和沙盒探索可以给固定路线提供素材，也可以给实时导航提供候选经验。先通过原型判断哪种形态更省维护，再决定下表各项的投入。

| 能力组 | 整体需求与验收 | 需要交付的业务闭环 |
| --- | --- | --- |
| 教程获取与编辑 | FR11–FR14；AC11–AC14 | 示范录制、资料生成和受控探索分别进入有来源和缺口的草稿，经作者编辑补齐；三种入口的实现时点可分别安排 |
| 教程验证、发布与发现 | FR15、FR17、FR19；AC15、AC17、AC19 | 有权作者检查、验证并发布固定版本；用户能按任务找到适用且可启动版本 |
| 维护与反馈处理 | FR16、完整 FR18、FR20；AC16、AC18、AC20 | 反馈接收、调查、修订、复核与处置结论可关联，支持撤下／回退及运行会话影响处理 |
| 引导适配与更多场景 | FR01–FR10 在新增范围内；AC01–AC10、NFR07 | 在明确网站、页面和任务范围内复用通用机制，验证专有前提与结果。Pages 和 Figma 的完整操作流程留待后续安排。 |

需要交付上表某项能力时，再从整体 SRS 取对应的需求和验收条件。

## 4. 主动复用与实施关系

每个增量设计时比较直接依赖、改造模块、借鉴机制和自行实现，沿用[现有 9 个项目的调研结果](../../research/notes/WebGuideAI-开源项目调研.md)。复用选择以需求适配、许可、固定版本、集成及维护成本为依据；需求重合是可利用的基础，不作为删功能或从零重写的理由。

Harness 分支沿用 TypeScript／React／WXT 扩展与 Node.js／Fastify 后端。旧模型接口可在原型分支查阅，新的模型交互随引导循环一起设计。已有 Pages 与生命周期实验继续作为网页观察和状态确认的参考。[工程配置](../design/WebGuideAI-工程配置与开发方式-v0.1.md)
