1. 目标是尝试完成一个完整项目，课程任务用于辅助引导。

5. 当前阶段暂不讨论商业化和付费模式。

## 2. 产品目标与目标用户

### 2.1 一句话定位

帮助用户带着具体任务，在真实网页上理解并完成操作；通过 Agent 学习或专家示范积累教程，并持续维护教程的适用性。

### 2.2 目标效果

- 用户知道当前应该做什么、为什么做，以及这一步是否完成。
- 用户点偏、切换模式或找不到入口后，能够得到符合当前状态的指引。
- 作者能够把已有经验或官方资料变成可检查的教程，并更新失效步骤。
- AI 生成的内容有来源、有适用条件，可以审核、修订和追踪版本。

原始提案中的“零延迟”“不怕改版”等表述在本版转为可测的响应、识别和恢复目标；不承诺任意网站、任意改版都能自动恢复。

### 2.3 产品角色建议

| 角色 | 主要任务 | 可操作范围 | 证据状态 |
| --- | --- | --- | --- |
| 学习者／操作用户 | 提出目标、选择教程、跟随引导、求助和反馈 | 自己的引导会话与获授权内容；自己在目标网站执行操作 | 用户本人及公开求助帖支持此类角色 |
| 教程作者／维护者 | 录制、生成、编辑、验证、发布和维护教程 | 自己或被授予维护权限的教程；查看经脱敏的相关问题记录 | 原提案、U05、U03 维护者回复支持；尚无本项目作者试用记录 |
| 平台管理员 | 管理平台角色、处理失效内容、查看运行情况 | 平台管理权限；关键管理操作留痕 | 为完整平台提出的角色，实际管理需求待确认 |

同一人可以兼任角色。平台角色与 GitHub/Figma 账号权限独立；平台管理员身份不赋予目标网站权限，教程作者也不能替学习者决定或提交其网页内容。

## 4. 完整产品范围与验证顺序

### 4.1 保留的完整产品能力

1. **教程获取**：Agent 阅读文档生成教程；在明确允许的练习环境探索流程；专家录制示范。
2. **教程整理**：编辑步骤、必要条件、结果检查、异常分支与适用范围；验证后发布。
3. **现场引导**：用户提出任务，在真实页面执行；系统解释、高亮、观察进度并提供纠偏建议。
4. **持续维护**：检索教程、记录版本、接收失效反馈、修订和重新发布。

### 4.2 建议的验证顺序

| 顺序 | 验证内容 | 要回答的问题 |
| --- | --- | --- |
| 第一组 | 三个场景的当前流程、状态和结果；少量人工整理的教程 | 能否定义可靠的步骤与完成条件，扩展能否取得必要信息？ |
| 第二组 | 引导、结果判断、暂停恢复、找不到入口后的处理 | 能否带用户完成任务，遇到异常会不会给错指引？ |
| 第三组 | 专家录制、文档生成、编辑、审核与发布 | 教程能否有效创建并经过检查？ |
| 第四组 | 受控探索、失效反馈、版本修订与回归检查 | 能否扩充教程来源并降低持续维护负担？ |

这是逐步验证完整项目的建议，不是已承诺的工期或最终版本裁剪。第一组可以使用人工整理内容，帮助明确教程结构，再检验自动生成能力。

当前不处理原生桌面客户端控制、任意网站通用保证、用户生产环境中的无人值守探索。首轮只验证桌面浏览器中的练习任务；浏览器支持清单待技术实验确定。

## 5. 三个典型场景与流程走查

本节先核对官方资料，后于 2026-11-16 在获授权的练习仓库与独立 Figma 文件中完成浏览器走查。详见[现场记录、截图和覆盖边界](浏览器场景走查-2026-11-16.md)。已发布测试站点、提交测试 review 并设置 Frame 自动布局；尚未测试 WebGuide AI 扩展，也未完成全部异常或真人用户试用。

### 5.1 SC01：发布一个简单 GitHub Pages 页面

**用户目标**：让练习仓库中的静态页面通过站点 URL 正常显示。

**证据**：N06、N09。**官方基线**：[D01](#d01)、[D02](#d02)。

**建议前提**：已登录；使用可发布 Pages 的练习仓库；具备配置发布源所需权限；选定已存在的分支和目录。本场景先采用分支发布与简单 `index.html`，不展开自定义域名及复杂构建流程。

**正常过程**：

1. 确认仓库、目标分支与目录，检查示例首页位于所选发布目录；确定本次页面的预期文字标记。
2. 用户进入仓库 Pages 设置，选择分支发布方式、实际分支与目录并保存。
3. 系统区分配置已保存、部署处理中、部署成功或失败；等待期间不反复要求保存。
4. 引导用户访问发布 URL，核对预期页面内容。
5. 只有目标部署结果与页面内容证据满足条件，才记录任务完成；无法观察其中任一项时标为待确认。

**文档核对结果**：官方资料允许选择分支与发布目录；入口文件需要位于发布源的顶层；配置后仍有构建部署过程。[配置发布源](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)、[创建站点](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)。

**异常分支**：

| 情况 | 期望系统行为 |
| --- | --- |
| 文件已上传但发布源未配置 | 解释两者区别，进入配置步骤；不宣布完成 |
| 权限不足或设置入口找不到 | 核对当前仓库与可见权限证据；未知时请求必要信息，不直接认定原因 |
| 分支或目录与首页不匹配 | 指出当前选择与已观察文件位置的差异，建议用户修正 |
| 保存后仍排队或页面暂不可用 | 显示等待状态，允许暂停后复查；超时后保留记录并排查，不直接判定配置错误 |
| 页面可访问但内容是旧版本 | 保持待确认，核对部署记录和预期标记 |
| 疑似账号限制或外部服务异常 | 展示证据与不确定性，提供支持渠道，终止无效循环 |

**验收示例 AC-SC01**：Given 练习页已有文件但发布源为空，When 用户开始发布引导，Then 系统将其识别为配置未完成；保存后进入等待；部署成功且访问页含预期标记后才判为完成。缺失证据时不得用“点击过 Save”替代结果。

**现场观察**：在英文界面中观察到文件已存在但发布源仍为 None、分支已选但尚未保存、保存后构建中；工作流关联提交 `0b5600a` 成功，实际站点含预期标记 `WG-SC01-20261116-v1`。选中的表单值不得当作已保存配置。

**判定修正**：同日技术实验发现站点上线后设置页仍显示“currently being built from the main branch”。该文字只作来源线索，不能独立判为实时构建中；实时状态须查关联工作流。见[可行性实验进度](Pages扩展可行性实验-2026-11-16.md)。

**仍待验证**：其他账号／语言、发布失败和超时样本、实际扩展跨域读取站点结果的方式及权限。无法自动取得页面证据时，应让用户提供结果，且记录为“用户确认”，与系统验证区分。

### 5.2 SC02：提交 PR review 中的待发布评论

**用户目标**：确认准备好的行级评论已通过 review 提交，使有权访问该 PR 的协作者可见。

**证据**：U03。**官方基线**：[D03](#d03)。

**建议前提**：已登录；拥有可参与评论的练习 PR；选择普通 Comment review 作为首轮路径。评论由用户准备和确认，不涉及自动批准或请求变更。

**正常过程**：

1. 确认当前仓库、PR 与评论对象。
2. 若存在 pending review，解释当前行级评论尚未随 review 提交；若没有，则从添加练习评论开始。
3. 引导用户在 Files changed 中找到当前界面的评审入口，检查评论和 review 类型；本次新界面显示 Submit review，旧文档使用 Review changes。
4. 用户自行点击 Submit review。
5. 系统观察对应 review 的已提交记录及评论状态；证据不充分则待确认。

**文档核对结果**：官方说明行级评论在提交 review 前处于 pending 且仅本人可见，并给出 Review changes 到 Submit review 的提交流程。[官方说明](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request?tool=webui)。

**异常分支**：

| 情况 | 期望系统行为 |
| --- | --- |
| 用户只添加了 pending 评论 | 解释未提交状态，不以评论框关闭或数量增加认定成功 |
| 用户直接发送了单条评论，已经发布 | 根据观察跳过草稿提交步骤，避免重复发评论 |
| 用户换到另一个 PR | 暂停原任务，确认目标后再继续 |
| 用户取消、丢弃或页面请求失败 | 保留实际状态；不当作已发布，不自动重发 |
| 找不到入口或权限未知 | 检查当前页面和相关状态，必要时转为解释与求助 |

**验收示例 AC-SC02**：Given 指定 PR 的一条评论仍属于 pending review，When 用户只点击 Add review comment，Then 系统保持未完成；When 用户确认内容并成功提交对应 review，Then 系统依据已提交记录更新结果。无重复提交。

**现场观察**：本次使用文件级评论，点击 Start a review 后显示 Pending，刷新仍保留；以 Comment 提交后出现独立 review 记录及原评论，Pending 消失。作者不能对自己的 PR 选择 Approve 或 Request changes。结果需关联目标 review，不能用其他自动 review 或评论总数替代。

**仍待验证**：行级评论入口、不同页面布局、提交失败、直接发布单条评论等路径，以及实际扩展如何关联同一个 review。仅从本人页面观察不能独立证明另一个账号实际看到了内容；必要时在练习仓库由第二位参与者核验。

### 5.3 SC03：找回 Figma 自动布局入口，并完成一次简单操作

**用户目标**：在可编辑练习文件中，为目标对象添加自动布局，并找到其布局设置。

**证据**：N03、N05、U01、U02。**官方基线**：[D04](#d04)、[D05](#d05)、[D06](#d06)。

**建议前提**：浏览器中的 Figma Design 练习文件；有编辑权限；明确选择目标对象。首轮先处理自动布局，绝对定位作为后续关联场景。

**正常过程**：

1. 确认文件、编辑权限、当前模式与已选对象；无法取得这些信息时明确指出缺口。
2. 检查当前对象是否已有自动布局，以及当前界面是否提供可用入口；已有布局则直接定位设置。Draw 不自动构成阻塞；仅在实际能力不足且有依据时建议切换模式。
3. 说明当前选择对应的自动布局操作，指导用户通过适用入口添加。
4. 检查目标对象的布局状态与设置是否出现，再确认任务完成。

**文档核对结果**：Draw 内部分 Design 功能不可用，切换可恢复相应工具；自动布局要求可编辑，官方提供右侧栏和快捷键等入口。[Draw](https://help.figma.com/hc/en-us/articles/31440394517143-Explore-Figma-Draw)、[自动布局概览](https://help.figma.com/hc/en-us/articles/360040451373-Guide-to-auto-layout-in-Figma)、[添加自动布局](https://help.figma.com/hc/en-us/articles/5731482952599-Toggle-on-auto-layout-in-designs)。

**现场修正**：本次选中 Frame 后，在 Draw 中仍能看到并成功启用自动布局，切回 Design 后状态保留；未复现 N03 的历史卡点。取消选择后右侧仅显示 Page，再选 Frame 后布局设置恢复。不能从“部分功能存在模式差异”推导为“自动布局必须切回 Design”。

**异常分支**：

| 情况 | 期望系统行为 |
| --- | --- |
| 当前为只读文件 | 说明编辑能力受限，不不断提示添加操作 |
| 未选对象或选错对象 | 引导明确目标；在对象身份不明时不继续修改属性 |
| 对象已使用自动布局 | 跳过重复添加，转到设置定位与解释 |
| 选项仍不存在或不可用 | 再查当前选择和适用条件；不能仅因切回 Design 就宣布解决 |
| 无法读取画布对象／面板状态 | 显示验证能力边界，允许用户确认或补充信息；不声称自动验证成功 |

**验收示例 AC-SC03**：Given 用户选定可编辑 Frame 且当前入口可用，When 用户添加自动布局，Then 系统确认该 Frame 的布局状态后完成，不因处于 Draw 强制切换模式。Given 未选对象，Then 引导先选择目标；Given 目标已启用，Then 跳过重复添加。若只观察到模式变化，不能认定布局已完成。

**仍待验证**：实际扩展对模式、权限与对象状态的读取可靠性，画布完整结构、是否需要额外截图或 Figma 接口；只读、复杂对象、子对象实际排列和重复添加等路径。当前浏览器工具可见属性面板，不等于扩展已具备同等能力。

## 7. 用户故事与验收条件初稿

每条使用 Given（前提）、When（动作）、Then（结果）组织可检验行为。所有验收条件是建议标准，不是已经通过的测试结果。

### US01：找到适合当前任务的教程

作为学习者，我希望用自己的话描述目标并查看适用教程，以便从当前任务开始。

- 对应：FR01、FR02、FR17；SC01、SC02、SC03。
- Given 用户描述目标且存在适用教程，When 发起检索，Then 展示教程目标、网站、适用条件与版本，选择后开始；Given 没有适用结果，Then 明确说明并转入 FR10，不伪造匹配项。

### US02：先知道当前条件能否操作

作为学习者，我希望知道模式、权限或对象选择是否满足条件，以免照着不存在的入口反复尝试。

- 对应：FR03；SC01、SC03。
- Given 某必要条件已观察为不满足，When 开始或继续教程，Then 先解释阻塞并给出适用的调整路径；条件不可读时标为未知，不当作满足。

### US03：清楚看到本步的目标与原因

作为学习者，我希望在当前页面知道应操作哪个控件及原因，以便理解并完成这一步。

- 对应：FR04、FR09；三个场景。
- Given 有唯一可确认的目标控件，When 展示步骤，Then 高亮与文字指向同一控件，用户仍自行执行；如果存在多个候选，Then 先消除歧义，不任意选取第一个。

### US04：知道任务是否真正完成

作为学习者，我希望系统区分中间动作与最终结果，以免遗漏最后一步。

- 对应：FR05；SC01、SC02。
- Given 仅点击保存或添加草稿评论，When 检查结果，Then 保持处理中或未完成；只有对应任务结果满足完成条件，才记录系统验证成功，并保留依据。用户确认与自动验证分别标记。

### US05：卡住后能重新找到适合当前状态的路径

作为学习者，我希望找不到控件或点偏后得到新的判断，以便恢复操作。

- 对应：FR06、FR10；三个场景。
- Given 目标不存在、不可用或用户报告指引不符，When 请求帮助，Then 重新检查当前状态并给出有依据的恢复建议；仍无有效路径时说明缺失信息并允许退出，不无条件重复原指令。

### US06：随时暂停并从实际进度继续

作为学习者，我希望暂停、退出或刷新后能够理解当前进度，以便按自己的节奏操作。

- 对应：FR07、FR08。
- Given 已记录部分进度，When 暂停或恢复，Then 暂停时停止自动推进，恢复时核对网站、任务对象与教程版本；状态已改变则重新判断，不盲目跳到旧步骤。明确结束后停止该会话的页面采集。

### US07：把一次示范变成教程草稿

作为熟练用户，我希望主动录制一次示范，以便复用已有操作经验。

- 对应：FR11。
- Given 作者已选择录制范围，When 开始、完成并停止示范，Then 生成可编辑的有序草稿，记录已采集与未能采集的步骤；停止后不再继续录制。

### US08：修正步骤与成功条件

作为教程作者，我希望编辑操作、前提和结果检查，以便教程表达完整流程。

- 对应：FR12。
- Given 作者可编辑某草稿，When 调整步骤并保存，Then 草稿保留修改，缺失必要条件或完成检查的步骤可被识别；已发布版本不被草稿修改覆盖。

### US09：依据官方资料生成可审核教程

作为教程作者，我希望用文档和目标生成草稿，以便减少手工整理步骤的工作。

- 对应：FR13。
- Given 可读取的文档与明确任务，When 发起生成，Then 返回来源、适用条件、候选步骤和待核实项；资料不足时指出缺口，结果保持草稿，生成失败可重新尝试而不覆盖现有版本。

### US10：让 Agent 在限定环境探索

作为教程作者，我希望限定练习环境、目标和操作边界后让 Agent 尝试流程，以便补充文档未写清的操作。

- 对应：FR14。
- Given 已指定隔离练习环境、允许范围和停止条件，When 开始探索，Then 操作留有轨迹，达到限制或越界前停止；未达到任务目标时记录失败，不生成“已验证成功”的结论。

### US11：先验证，再发布教程

作为教程作者，我希望检查步骤可执行性和完成条件后发布，以便学习者知道教程是否经过验证。

- 对应：FR15。
- Given 有草稿及声明的验证环境，When 校验和人工检查完成，Then 记录通过或失败与依据；未通过的不能标成验证通过，发布形成可识别版本。

### US12：更新教程并保留历史

作为维护者，我希望用新版本修复失效步骤，以便控制变更并保留可用历史。

- 对应：FR16。
- Given 有已发布版本，When 创建修订或回退，Then 保留历史与变更原因；运行中的会话仍关联原版本，若需切换则说明影响并重新检查进度。

### US13：反馈卡点并跟进维护

作为学习者，我希望提交卡住的位置和实际情况；作为维护者，我希望看到与版本关联的反馈，以便定位并处理问题。

- 对应：FR18、FR20。
- Given 会话停在某一步，When 用户检查附加内容后提交反馈，Then 记录任务、步骤、教程版本和问题描述；维护者可关联修订与处理结论，统计不暴露无关页面内容。

### US14：按职责使用平台功能

作为平台用户，我希望编辑和管理行为受到权限约束，以便维护自己的教程与记录。

- 对应：FR19、FR20。
- Given 用户没有目标教程的维护权限，When 通过界面或直接请求修改、发布或撤下，Then 服务端拒绝且内容不变；获授权者操作成功并留下对应记录。管理员也不因此获得用户目标网站的账号权限。

## 8. 非功能需求建议

以下指标为初始验证目标。测试前固定浏览器、版本、样本、网络和计时口径；性能数字不是已经实测的承诺。

| 编号 | 需求及建议标准 | 验证方式 |
| --- | --- | --- |
| NFR01 结果可靠性 | 预先定义的负例集中，出现“草稿未发、部署中、旧页面、对象未知”等情况时，不得误报系统验证成功；观测不足进入待确认 | 按 SC01–SC03 建正反例清单，逐项保存预期与实际结果；报告样本数与误判，不能只报成功率 |
| NFR02 响应与可取消性 | 页面及目标已就绪、无需模型时，步骤更新建议 p95 ≤ 500 ms；需远端处理时 1 秒内显示等待，建议 30 秒未完成后给出超时/重试/退出；目标值待实验校准 | 明确计时起止点，每类至少记录 30 次；网站加载与部署等待单列，取消后迟到结果不能推进已结束会话 |
| NFR03 页面数据控制 | 页面采集限于用户开启的任务和明确范围；默认不上传密码、令牌、Cookie 或无关内容；反馈附件可预览删减 | 用含测试敏感字段的样例检查实际请求和日志；暂停/结束后验证停止约定范围的采集；脱敏不能依赖模型自行遵守提示 |
| NFR04 权限隔离 | 学习者、作者、管理员的写操作在服务端执行授权；不能通过替换教程/会话 ID 访问他人非公开内容 | 对跨账号读取和修改进行反例检查，并核对被拒请求没有改变数据 |
| NFR05 可恢复与可追溯 | 会话、步骤结果、教程版本及必要变更可关联；失败和重试不导致重复发布内容或覆盖已发布版本 | 验证刷新、网络失败、超时、重复请求、草稿编辑和版本切换路径 |
| NFR06 易用性与验证透明度 | 当前步骤、暂停、退出和求助可找到；高亮配有文字说明；系统观察、用户确认和待确认三类结果可区分 | 观察真实使用者完成三类任务，记录任务完成、求助、误操作和理解情况；可使用快捷键到达引导控件 |

本版不将少量场景通过等同于通用能力已成立。真实用户比较时，分别记录：任务结果、人工干预、错误指引、耗时与主观理解；与普通文字说明比较，保留不改善或更差的结果。

## 9. 状态、数据与能力边界

### 9.1 引导状态的最低约定

会话至少能表达：待开始、引导中、等待外部结果、暂停、阻塞、待确认、已完成、已结束。步骤至少记录未开始、进行中、已验证、用户确认、失败或跳过；跳过必须有理由。

“已完成”需要明确依据，结果标签区分“系统验证”和“用户确认”。用户确认的步骤不能在统计中被当成系统自动验证成功；存在未经确认的关键结果时，会话保持待确认。重复点击、重新加载或取消，不得隐式变成完成。

恢复建议不得静默改写共享教程。当前会话可以在明确说明后采用临时修正；长期修订通过草稿、检查和新版本发布完成。

### 9.2 需要记录的信息类别

| 信息 | 最少需要表达什么 |
| --- | --- |
| 教程 | 目标网站、任务、适用条件、来源、步骤、完成检查、异常分支、版本与发布状态 |
| 步骤 | 目的、操作说明、目标依据、前提、预期结果、无法确认时的处理 |
| 引导会话 | 用户任务、目标网页对象、使用版本、当前位置、结果类型及必要证据 |
| 反馈与维护 | 对应任务/步骤/版本、用户描述、经检查的附加信息、处理结论与相关修订 |
| 学习与生成记录 | 资料来源或示范、探索范围、已验证部分、失败与待核实项 |

这些是业务信息要求，不规定数据库表、选择器格式或接口结构。存储位置、保存期限和删除方式需在数据设计时明确。

### 9.3 关键能力边界

- 用户在真实目标网站自行操作；提交评论、保存发布设置等动作仍由用户决定。
- 自动探索与现场引导是两条不同流程：前者仅在指定练习环境开展，后者观察并指导用户。
- 无法读取的账号权限、本地 Git 历史或 Figma 对象状态必须标为未知；不能仅凭按钮缺失编造根因。
- 页面、教程资料和录制内容作为待分析信息，不应改变系统的操作边界或让系统泄露其他内容。
- 浏览器侧是否能取得必要结果，是技术实验问题。不能读取时采用补充信息或用户确认，并保留验证等级。
