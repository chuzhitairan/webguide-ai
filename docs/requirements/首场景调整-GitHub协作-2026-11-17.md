# 首场景调整：GitHub 小组协作

日期：2026-11-17。类型：交付范围与展示顺序调整；完整系统目标继续依据 [SRS v0.2](WebGuideAI-SRS-v0.2.md)。

## 已确认的调整

发起人提出：“这个场景我觉得可以替代 Pages，可以在我们展示时优先放出来。”据此，首个交付与优先展示场景从 GitHub Pages 调整为 **GitHub 小组协作入门**。教程创建与维护仍在首个引导闭环之后推进。

Pages 的实验、观察和专有验收保留，作为已有技术证据与后续教程候选。原场景编号 SC01、B01–B12 和既有日志含义不变；新场景暂记 SC02，避免把 Pages 的完成证据套到协作任务。

## 本次需求来源

发起人看到正式课程仓库中的 6 个 Issue、1 个 PR 和 1 个 Open Project 后，询问这些对象的用途、关系，以及是否为课程要求。获得解释后，发起人指出不熟悉 GitHub 的人需要花时间熟悉这种管理方式，并提出优先展示此场景。

这是一条实际发生的概念理解需求。尚未记录该参与者独立完成认领、提交 PR 的过程、耗时或失败，因此不据此声称产品已改善效率，也不计作独立访谈。

## 建议的首个演示切片

以下为首个演示切片方向；发起人同意继续细化，详细路径、前提、结果规则与 14 项验收现已整理为 [SC02 规格 v0.1](GitHub协作首场景规格-v0.1.md)，新增细则仍为草案。

**目标用户：**已登录 GitHub、已有课程仓库访问权限，第一次参与仓库协作的成员。

**任务：**理解并认领一项明确任务，在浏览器中修改指定文档，提交到独立分支并发起正确的 PR，让其他成员可以评审。

| 阶段 | 用户要理解或完成的事 | 引导与核对重点 |
| --- | --- | --- |
| 理解任务 | 分清 Issue、PR、Project；看懂卡片和验收条件 | AI 结合当前任务解释用途，页面指示对应入口 |
| 认领 | 确认目标仓库和 Issue，将任务指派给自己 | 检查正确对象与实际指派；无指派权限时给出组长分配路径 |
| 修改 | 打开已准备的指定文档，完成一项小修改 | 指示文件和编辑入口；内容由用户编写，不把点过编辑按钮当作已提交 |
| 提交 PR | 保存到独立分支，核对基准／来源分支及修改后发起 PR | 核对仓库、分支、修改和关联任务；区别提交记录与 PR |
| 等待评审 | 理解 Open／Draft、Review 和 Merge 的区别 | 显示“已发起、待评审”；有评审者和权限时引导请求评审 |

首段演示建议以“正确 PR 已建立，任务进入待评审”作为成功节点。评审、修订、批准、合并、关联 Issue 关闭及看板收尾可组成后续角色段落；等待其他成员时保留等待状态，不宣称整个协作流程已完成。PR 是否为 Draft、何时请求评审，须服从该任务真实的交付条件。

展示使用单独练习 Issue、文档与分支，避免为了演示修改真实课程访谈结论、批准未审阅材料或合并未完成的课程 PR。现有课程 PR #3 的访谈和真人评审条件继续适用。

## 继承与需要改写的部分

- **继续使用：**桌面 Edge、英文 GitHub 页面、中文说明；侧栏和页面内高亮；用户自行操作；规则核对结果；AI 解释答疑；偏离处理、暂停继续和最简反馈。
- **复用已有通用设计：**任务与教程版本绑定、目标唯一性、消息修订、过期回答隔离、失效高亮撤销，以及已选技术栈方向。
- **重新定义场景规则：**目标 Issue／账号／文档／分支／PR 的身份关联，认领权限，提交与 PR 创建的区别，评审等待及多角色边界。Pages 的部署 SHA 和站点标记不能替代这些条件。
- **暂不扩入首段：**Git 命令行安装教学、复杂冲突解决、Fork 贡献、仓库管理权限配置、完整 Projects 管理教程，以及系统代用户提交、评审或批准。

场景更贴近课堂任务，但不能据此断言实现更简单。PR 的对象与版本关联、权限差异和异步网页行为仍需设计与验证；已有 Pages 实验没有验证这些新条件。
