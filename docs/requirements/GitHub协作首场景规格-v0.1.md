# GitHub 协作首场景规格 v0.1

更新：2026-11-19。状态：SC02 路径与验收草案，供设计与实现使用；尚未实现或完成真实页面验证。

依据：[完整系统 SRS v0.2](WebGuideAI-SRS-v0.2.md)、[场景调整决定](首场景调整-GitHub协作-2026-11-17.md)、[版本交付范围](版本交付范围-2026-11-17.md)。本稿细化新场景，不改写整体 FR／UC，也不复用 Pages 的 SC01／B 编号。

## 1. 场景目标与交付终点

**用户目标：**第一次参与小组仓库协作的成员，理解任务，认领指定 Issue，通过浏览器修改一份文档并提交可供他人评审的 PR。

**本段终点：**系统核对本次任务对应的 PR 已正确建立且可交接评审。正常路径显示“本段提交已验证，等待成员评审”。如同一 PR 当前有失败的 CI 检查或评审请求修改，引导停在交接步骤，并给出处理提示。

首版采用 **同仓库、单成员提交、单文档小修改**。评审／修订／合并及看板收尾作为后续角色段；用户看到其含义和真实状态，但本段不指导或代做评审合并。

## 2. 前提与任务参数

| 项目 | 支持边界／要求 |
| --- | --- |
| 环境 | 桌面 Edge、英文 GitHub.com 页面、中文引导；登录、双重验证和接受邀请由用户完成 |
| 成员 | 已登录的目标成员已获仓库写权限，能在同仓库创建工作分支；“仓库能打开”不能单独证明写权限 |
| 仓库与分支 | 已有提交和可读基准分支，允许创建指定工作分支；保留原分支保护，不要求管理员绕过 |
| Issue | 同仓库、明确编号和验收条件、仍开放，允许本成员认领；已指派别人时先处理分工，不覆盖别人 |
| 文档 | 基准分支已有指定 Markdown 文档；练习任务只修改一个明确段落或占位内容，无编译依赖 |
| 改动目标 | 任务给出可机械核对的小修改，例如替换指定占位句，含本次练习唯一标记；真实访谈内容不靠标记判断质量 |
| 评审者 | 由组长安排另一位真人；未配置评审者不妨碍先建立 PR，但必须说明尚未请求评审 |
| Projects | 用于解释卡片和状态关系；看板访问和写权限独立检查，不作为本段必需条件，也不要求编辑看板 |

任务参数包含：目标仓库、Issue 编号、成员账号、基准分支、拟用工作分支、文档路径、预期改动、练习标记、可选评审者和 Project 入口。创建后绑定实际提交身份及 PR 编号／地址。用户无需事先知道提交 SHA；系统在提交后获取并关联证据，无法可靠获取时保持待确认。

每次练习使用独立分支和标记。已有同名分支或 PR 时先核对归属与内容，不覆盖或重复创建；从别的分支继续需要用户确认目标影响。

## 3. 用户路径

### SC02-A：首次提交

| 步骤 | 用户操作与目的 | 页面指示与推进依据 |
| --- | --- | --- |
| 1 确认任务 | 查看指定 Issue，理解目标、交付物和条件 | 指示 Issue 标题／正文；确认仓库、编号及成员。简述 Issue 是任务、PR 是提交修改、Project 是任务看板 |
| 2 认领任务 | 在 Assignees 中指派自己 | 指示相应入口；读取保存后的指派结果。已指派自己可跳过操作；别人负责时提示协商；无权限转受阻 |
| 3 创建工作分支 | 从确认的基准分支创建本次独立分支 | 指示分支入口、名称与来源；创建后核对当前仓库和分支。先分支后编辑，避免在受保护分支上修改 |
| 4 编辑文档 | 打开指定路径，在工作分支修改指定内容 | 指示文件、编辑器和目标段落；用户输入，系统不替写整段正文。预览仅用于核对，尚未提交时仍为未保存 |
| 5 提交修改 | 核对差异、填写提交说明，保存到工作分支 | 核对提交弹窗选择“提交到当前工作分支”及目标分支名；若选另建分支先更正，去向未知先停。保存后检查该分支提交与不可变文件的 Code 源码，建立本次提交锚点；点击提交或提示不能单独通过 |
| 6 准备 PR | 打开比较／新建 PR 页面，核对 base、compare 和 Files changed | 指示基准／来源分支和差异；要求正确仓库、不同分支、目标文档及预期修改。无差异或混入其他改动时先处理 |
| 7 发起 PR | 填写说明，引用目标 Issue，确认已完成本任务要求后创建普通 PR | 指示标题、正文和提交入口；说明预览页不等于 PR 已建立。未完成内容可保留 Draft，但不能算本段已交付 |
| 8 核对并交接 | 查看实际 PR，了解待评审状态；有合适评审者时由用户请求评审 | 核对实际 PR 编号、作者、仓库、base／head、提交与文件改动、任务引用、Open 且非 Draft；区分“尚未请求”和“已请求但未评审” |

GitHub 官方说明支持从工作分支修改文件并建立 PR；本稿采用先建分支的路径，适配受保护 main。菜单名称作为定位线索，精确定位与当前真实页面行为在实现适配时验证。[分支管理](https://docs.github.com/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository)、[编辑文件](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files)、[创建 PR](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request)。

### SC02-B：已有进度／已有 PR

从当前页面重新核对任务对象及有效观察，定位到尚未满足的步骤；不要求重新认领、重复提交或重复建 PR。编辑器存在未保存输入时先提醒保留并由用户决定是否导航，不自动跳页丢失输入。

已有 Draft 显示“草稿已建立，尚未交付评审”；用户确实完成内容后可自行标为 Ready，再核对。已有正确普通 PR 可直接进入交接；已关闭未合并显示未交付，已合并显示历史提交结果及实际状态，不再要求创建重复 PR或报告仍在等待评审。历史结果不作为本次新练习标记的成功证据。

### SC02-C：受阻、偏离与退出

| 情况 | 产品行为 |
| --- | --- |
| 未登录／未接受邀请／明确无写权限 | 提供登录、接受邀请或联系组长路径，停止不适用的操作指示；不扩大权限或静默切换到 Fork 路线 |
| 控件缺失且原因未知 | 显示无法确认，提供重新核对／求助；不能只凭缺少按钮断言无权限 |
| 工作分支同名、不是从目标基准创建、或混入其他修改 | 展示冲突对象，用户确认改用干净分支或调整任务；不覆盖分支、不隐藏额外差异 |
| 保存响应慢、创建 PR 响应未知 | 显示核对中并查现有结果；不要连续重复提交或创建 |
| 错误仓库／账号／Issue／base／head | 撤销旧指示并说明不一致，返回正确对象或明确重设目标；旧证据不迁移 |
| 用户打开新标签、SPA 导航或目标重建 | 同任务关联正确页面并重查；唯一可见目标重新定位，不在旧坐标保留指示 |
| 用户暂停、关闭侧栏、返回上一步 | 遵循通用会话规则；返回只改变查看步骤，不撤销网站操作，也不重复提交 |

## 4. 完成与证据规则

任务绑定“仓库＋Issue＋成员＋基准／工作分支＋文档＋预期改动＋教程版本”。提交后固定本次提交身份，再绑定真实 PR。后续 head 或 base 变化时重新核对差异与关联，不能沿用旧通过；不因它们属于同一仓库或标题相似就匹配。

本段系统验证需同时具备当前可用证据：

1. 目标 Issue 中本成员确为负责人，或组长已将任务指派给该成员；实际指派与仅口头确认区分。
2. 预期改动已提交到本次独立分支，提交身份及目标文档内容可核对；工作分支不同于基准分支。
3. 实际 PR 属于目标仓库、作者为该成员，base／head 与目标一致；PR 当前版本包含本次提交和预期修改，变更文件仅为该指定文档。
4. PR 说明引用正确 Issue。首段采用普通任务引用，不要求关闭关键字或自动关闭关系；引用文本不等于任务已完成。
5. PR 为 Open 且非 Draft，并且未出现与上述证据冲突的已知更新。五项证据齐备时显示“本段提交已验证”、依据与观察时间，按当前交接状态补充提示。

任一关键证据不全／读取失败／过期，显示待确认及补查位置；实际对象冲突、明确拒绝或操作失败时显示受阻。用户确认“我已经提交”可记录为用户确认，不能代替系统验证。

对练习文档只验证约定的文件、提交与文本修改。评审、CI 与合并状态各有实际状态。已核对的 PR 当前有 CI 失败时显示“本段提交已验证 · CI 检查失败，需处理”；评审请求修改时显示“本段提交已验证 · 评审请求修改，需处理”；同时出现时显示两项。引导保留在交接步骤，用户处理后重新核对。提交证据过期、缺失或冲突时，撤下当前“本段提交已验证”提示并说明原因。[PR 状态说明](https://docs.github.com/en/pull-requests/reference/pull-requests)。

请求评审是有权限时的后续交接动作，显示实际请求对象与结果；未安排真人时说明缺项。请求产生通知，产品只引导用户自行确认执行。[请求评审](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/requesting-a-pull-request-review)。

看板状态单独呈现：GitHub Project 的 Open 只说明项目未关闭，不能推出其任务未完成；卡片移动到 Done 也不能证明 PR 合并。Issue 自动关闭依赖正确关联及目标分支等条件，不能承诺建立或合并任何 PR 都关闭 Issue。[Issue 与 PR 关联规则](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)。
