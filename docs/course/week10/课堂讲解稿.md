## 讲解正文

### 1. 项目与干系人

我们的项目叫 WebGuide AI，目标是帮助用户在真实网页上理解并完成具体操作。用户有时已经拿到教程或问过 AI，仍然不知道当前页面该点哪里，或者操作完以后不确定是否真正成功。

完整系统有三类产品角色：操作用户、教程作者与维护者、平台管理员。我们既要考虑用户如何跟着教程完成任务，也要考虑教程从哪里来、怎样验证发布，以及页面变化后由谁维护。

### 2. 调研怎么做

目前我们采用了公开讨论分析、开源源码研究和场景走查。前两轮分别保留 5 个和新增 9 个讨论主题，来源包括 GitHub Community、Figma Forum 和技术写作社区；我们下载研究了 9 个开源项目，并保留固定版本和代码索引。另外，项目发起人完成了一次 Pages 人工引导体验。

这里的讨论数量不是访谈人数。发起人已经熟悉部分流程，也不等于独立新手试用。独立访谈目前尚未完成，我们已经安排访谈提纲与有限分工；课前如果补齐，会按实际记录更新这一段。

### 3. 三类典型问题

第一类是“说明有了，还是不知道如何落到界面”。一位 Figma 新手把 ChatGPT 生成的顶栏布局规格带到社区，询问如何继续创建子对象。这说明详细说明和可执行步骤之间仍有距离。我们的发起人也明确提出，希望该点的位置直接在页面高亮。因此系统需要把说明与当前真实目标对应，同时保留原因解释。

第二类是“找不到控件，不一定只是按钮改位置”。Figma 的一个讨论中，原作者以为更新移除了自动布局选项，后来发现切到了 Draw 模式，切回 Design 后恢复。这提醒我们要先检查模式、权限和对象等前提。无法确认原因时，应说明未知，不能反复指向不存在的菜单。

第三类是“做过动作，不等于任务完成”。GitHub 有用户把 Pending 评论理解成已经提交；Pages 的求助中，也有人 HTML 已上传却不清楚发布源是否启用。因此我们希望把动作、等待、失败和最终结果分开。高亮解决入口问题，规则检查解决结果问题，AI 负责帮助用户理解它们。

### 4. 为什么借鉴现有项目

相关功能已有成熟探索。OnTheWay 提供录制、步骤生成和引导的参考；Usertour 有编辑发布和元素条件监测；Driver.js 可以承担页面高亮与提示气泡。我们主动复用这些已有能力，关注集成之后能否可靠完成用户任务。

当前研究是静态源码阅读，没有做这些产品的运行效果排名。Driver.js 也不会替我们判断一个 Pages 任务是否发布了正确版本，业务核对、权限和跨页状态仍需实现与验证。

### 5. 完整范围与首个增量

完整业务是：从示范、文档或受控探索形成草稿，编辑和验证后发布；用户找到教程，在真实网页接受指引并核对结果；出现问题后反馈、修订或撤下教程。

我们将 GitHub 小组协作入门作为首个交付及优先展示场景。这来自一次真实提问：看到仓库中的 Issue、PR 和 Open Project 后，发起人需要先理解它们的关系以及接下来做什么。建议先引导已获仓库权限的新成员认领 Issue、在浏览器修改文档并发起 PR；评审合并与看板收尾可组成后续角色段落。首版支持桌面 Edge、英文 GitHub 页面和中文指引，包含高亮、规则核对、当前步骤答疑、暂停继续和最简反馈，随后建设教程创建与维护。新场景详细验收仍需细化。

我们已经整理了 14 条用户故事，覆盖学习者、作者与平台管理。例如，US03 要求高亮指向唯一可确认的控件；US04 要求按实际结果判断完成；US07 是录制示范形成草稿；US12 是修订教程时保留历史。后两者属于后续增量，完整系统需求与版本交付次序分别管理。

一个拟定的验收例子是：文档已有提交记录，不代表 PR 已发起；PR 已建立，也不代表已经过成员评审并合并。系统需要核对正确仓库、分支、任务及 PR 状态，明确本段“已提交、待评审”的结果。证据不够就显示待确认，AI 的回答不能把规则结果改成成功。

### 6. 已有可行性与风险

我们做了只读的 Pages 状态实验，观察过配置、工作流和站点内容，并检查清空观察、证据不足与范围外页面。另一个本地实验对侧栏关闭、暂停、跨标签页与旧高亮撤销取得了部分记录。这些支持通用机制设计；首场景调整后，Issue、提交与 PR 的专有核对仍需验证。正式产品还未搭建，课堂上的真实仓库展示用于说明需求和管理流程。

主要技术风险是动态页面定位和跨页证据关联。应对方式是目标唯一性检查、失效先撤销高亮、会话绑定任务和版本，并把 AI 解释与完成规则分开。

### 7. 接下来做什么

接下来补独立访谈，将其发现与反例纳入报告，再通过真实组员 Review 完成课程 PR。需求方面继续细化用例、非功能场景与追溯关系，准备第三次课的 SRS 评审。工程方面按既有设计推进第一个可运行闭环。

本次希望向教师确认选题是否适当，并检查调研和范围是否还缺关键角色或场景。仓库、报告 PR、访谈和审核状态将按真实进度展示。

可能的问题：已有引导工具为何还做？——主动复用现成能力，验证面向第三方网页的引导、结果核对与维护闭环。为什么先 GitHub 协作？——贴近组员和课堂的真实任务，能展示概念解释、页面操作和结果核对；Pages 实验继续作为技术证据保留。证据能代表所有用户吗？——不能；本轮是探索性调研，独立访谈和真实试用继续验证。
