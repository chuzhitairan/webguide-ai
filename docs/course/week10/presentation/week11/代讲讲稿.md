## 00:00–01:00 我们在解决什么问题

*展示 PPT 第 1–2 页，或停在 SRS 第 1 节「目标与需求来源」。*

大家好，我们做的是 WebGuide AI，是一款直接画在浏览器网页上的操作引导扩展。

选题的痛点就来自我们这门课。课程要求用 GitHub 做小组协作，很多同学刚上手时，心里明明知道“我想去看看队友提交的那段修改”，或者“我想把某个 Figma 图层导出”，但面对密密麻麻的英文菜单还是不知道该点哪里。如果平时去问通用 AI，还得截图、切窗口，AI 回你一段纯文字说“请点右上角某某图标”，切回网页还是得自己满屏幕找。

我们的做法是：用户在浏览器侧边栏直接用大白话输入目标，扩展读取当前网页，让 AI 判断下一步该操作哪里，**然后直接在当前网页的按钮上画一个蓝框并配一句提示**。点击、输入还是由用户自己决定；用户操作完、页面发生变化后，扩展会重新看一遍页面，判断是继续指下一步，还是已经完成。

为了防止 AI 像平时聊天那样“还没走到就瞎报完成”，我们在需求里把终点拆得很细。同样是找东西，**“只是找到入口”**和**“真的打开进入页面”**，结束标准完全不一样，下面会用两个例子详细说明。

## 01:00–02:40 用例图和交付范围

*切到 PPT 第 3 页；如果投影字太小，直接切到浏览器单独打开的「用例图全图」并放大。先指左侧 3 个角色，再从上到下指中间 3 个区块，最后指右侧（上：模型服务，下：目标网页）。*

这是我们的完整功能用例图，一共 20 个用例。

先看左边三个主参与者：操作用户、经验维护者、发布管理员。中间系统边界框里按开发阶段分成上、中、下三个区块：

- **最上面是这一轮先交付的「组内预览」（13 个用例）**：操作用户填好自己的模型配置、输入目标，就能跟着网页蓝框一步步操作；目标有歧义时可以回答澄清，遇到模型超时卡住也能保留原目标继续。
- **中间是第二阶段的「本机经验」（4 个用例）**：用户自愿开启本机记录后，经验维护者可以从成功和卡住的记录里整理好用线索，再拿新任务做对照验证。
- **最下面是第三阶段的「共享经验」（3 个用例）**：操作用户可以贡献脱敏后的经验，发布管理员负责把关发布，经验失效时也能及时停用或回退。

因为目前本机实验对比还没看出经验提示有稳定收益，这轮我们先把最上面“组内可独立使用的实时引导”做扎实，后两块明确划为后续范围。

再看右边两个次参与者：上面是**模型服务**，根据用户目标和网页线索给出下一步建议；下面是**目标网页**，提供当前页面里真实的按钮、图层和选中状态。模型提出建议后，扩展会先回目标网页核对这个控件确实存在、可点击，才会把蓝框显示给用户。

## 02:40–04:00 场景一：Figma 找到导出入口（NAV-UC06）

*切到 PPT 第 4 页，或回到 SRS 第 4.1 节，指向流程图的「核对图层和可用控件」和「需要时滚动，复查并高亮入口」。*

第一个场景是在网页设计工具 Figma 里，用户说「帮我找到 Frame 1 的导出设置入口」。

先说一下这个界面的坑：Figma 右边属性栏里，没选具体图层时显示的是“整个页面的导出（Export）加号”，选中 Frame 1 图层后显示的才是“这个图层自己的导出加号”，两个按钮长得几乎一模一样。

所以扩展不会一看到加号就乱指。它会先看用户当前有没有选中 Frame 1；确认目标属于 Frame 1 且按钮在屏幕外面时，扩展可以直接帮用户把面板滚到眼前；如果当前线索还不够，侧边栏会先提示用户选对图层或手动滚动。

这个场景的关键词是**“找到入口”**。所以验收标准是：蓝框必须准确落在 Frame 1 那一栏真正可点的加号上，同时侧栏报告“已找到”，页面提示随后自动收起。如果扩展只看到了“Export”标题文字，或者指到了别的图层的加号，都算没找到，必须继续找。另外如实说明一下，我们在真实 Figma 复测中出现过“滚动后蓝框已经指对，但侧栏没自动收尾”的情况，所以验收时把“高亮落点”和“侧栏收尾”分开记录并继续复测。

## 04:00–05:30 场景二：GitHub 打开指定详情（NAV-UC07）

*切到 PPT 第 5 页，或滚到 SRS 第 4.2 节，指流程图的「用户打开」和「核对通过」两个节点。*

第二个场景回到 GitHub，用户说「带我打开仓库里第 1 号 PR 的详情」。

这里的关键字是**“打开详情”**，终点不是列表里的那一行字，而是必须真的进到详情页里面。列表页很多时候标题不在第一屏，扩展会先按 `#1` 局部补看列表条目，在对应链接上画蓝框，等用户自己点击进去。

点进去之后，扩展不会立刻报完成，而是会重新检查两件事：第一，确认当前确实是第 1 号 PR；第二，详情页正文的可用控件已经加载出来了，比如复制分支名的按钮。如果页面还停在 PR 列表，或者没登录跳到了登录页、打开了别的 PR，都不算完成，侧栏会提示先登录或者继续指路。

我们在练习仓库里拿第 1 号 PR 做过测试，分别从“PR 列表页”和“已经在详情页里”两个起点各试了 2 次，4 次都核对正确并正常收尾。这个例子可以从 GitHub 上第 19 号故事 Issue（`#19`）查到对应的需求，在追溯矩阵里找到实测记录。

## 05:30–07:20 性能、安全、可用性怎么验收

*切到 PPT 第 6 页，或滚到 SRS 第 5 节；老师追问具体复现步骤时，切浏览器标签页的「验收与证据」第 2 节。*

三条非功能需求，我们都写成了可以实际测量和复现的验收方法：

**性能（NAV-NFR01）。** 页面和域名权限都准备好时，从用户点击「开始引导」开始计时，要求 **1 秒内**在侧栏看到“正在连接或查看页面”的状态反馈，让用户知道系统没有卡死。同时系统限制单次模型请求最多等 15 秒，一轮引导总等待预算 45 秒，避免死等。目前 15 秒和 45 秒的超时控制已经有自动化测试覆盖，1 秒的首条反馈还待独立计时验证。

**安全（NAV-NFR02）。** 核心原则是“大模型只需要看指路用的页面线索，不该看的绝对不带出去”。我们设计了一个包含虚构密码、表单值、网页 Cookie 和诱导性干扰文字的模拟网页，发起引导后去检查模拟服务端实际收到的请求正文和扩展本地日志，确认这些敏感内容出现次数必须为零，且用户的 API Key 只会作为凭据发往用户自己授权的模型域名。目前直连与配置边界已测过，这套安全组合样页待执行。

**可用性（NAV-NFR03）。** 如果模型连续超时、自动重试还是失败，扩展会暂停，但**不会把用户原来的目标丢掉**；暂停期间就算页面自己变化了，扩展也不会在后台乱发请求烧额度。等用户点「继续引导」时，它会带着原目标重新观察当前最新的页面继续指路。我们在自动化浏览器回归里专门验证过这一条：故意让第一次超时、第二次返回无效结果触发暂停，在暂停期间把页面上的旧按钮换掉，点继续后它确实按新按钮重新指路并顺利完成。

## 被追问时可以这样答（现场救场速查）

- **现在组员能装来用吗？**
  可以。从 GitHub Release 下载插件包，解压后用 Chrome 或 Edge 的开发者模式加载，再填自己的同济 API 密钥就能试用。[v0.0.1 插件包](https://github.com/chuzhitairan/webguide-ai/releases/tag/v0.0.1)
- **和直接把截图发给 ChatGPT / 通用 AI 助手有什么区别？**
  截图问答看到的是发出去那一刻的画面。我们的扩展直接在当前网页的控件上画蓝框，用户操作后还能读到选中的图层和页面变化，用新的信息继续指路。
- **为什么不一开始就做团队共享经验库？**
  我们在 Figma 和维基百科上做过有无预设经验的小样本对照，目前还没看出稳定收益。这版先留一个默认关闭的试验开关，等组员试用发现哪些地方确实需要经验，再验证本机提炼和团队共享。
- **你们前面交过一个“做 GitHub Pages 教程”的方案，为什么改成了现在这样？**
  真实走查时发现网页界面和用户起点变化很大，提前写死的教程步骤一换页面就会失效，所以从 11 月 20 日起做了正式的需求范围调整，在文档的《需求变更记录》（DC01–DC05）里完整记录了原因和影响，旧方案保留在 SRS v0.2。
- **如果老师说大模型 API 不算课程规定的外部集成（如第三方登录/支付/地图）怎么办？**
  先请老师说明认定条件。如果要补别的接口，记进评审意见，再评估哪种集成能解决组员实际需要。
