# WebGuide AI · 讲者备注

全篇 8 页，按约 8 分钟安排，包含指图与停顿。

## 第 1 页
建议用时：20 秒

大家好，我们的项目叫 WebGuide AI。我们想做一个浏览器里的任务引导工具：需要操作的时候，直接在当前页面指出位置，说明原因，并帮助用户确认结果。先从我们自己接触到的 GitHub 小组协作讲起。

材料来源：docs/course/week10/调研报告.md §4–6；docs/course/week10/发起人体验记录.md

## 第 2 页
建议用时：55 秒

这是我们初始化小组仓库时保存的真实看板。对熟悉 GitHub 的人，任务卡片和状态列很直观；但第一次参与协作的人，可能还不知道从哪张卡片开始，也不清楚接到任务以后去哪里改、改完又怎么交给同伴。这里真正要解决的，不只是某一个按钮叫什么，而是如何沿着当前界面完成一件具体的事。下一页就用一次文档修改，把这条路径展开。

材料来源：docs/course/week10/evidence/course-board-2026-11-17.jpg；docs/course/week10/调研报告.md §4–6；docs/course/week10/发起人体验记录.md。展示历史初始化视图，图片裁掉下方区域以突出任务与状态。

## 第 3 页
建议用时：65 秒

假设任务是给小组仓库补一段快速上手说明。Issue 是任务单，分支给修改一个独立位置，提交记录改动，PR 把改动交给同伴检查，之后再评审合并。但知道这套流程，实际操作时仍然有一道坎：到了眼前这个页面，该点哪里？已经有了分支或提交，要从哪一步继续？现在的结果到底对不对？这就是我们做 WebGuide AI 的直接动机：把教程和用户正在做的那次任务连接起来，让引导跟上实际页面和进度。接下来看看哪些基础能力可以借鉴。

材料来源：docs/requirements/GitHub协作首场景规格-v0.1.md；docs/design/GitHub协作适配契约-v0.1.md；https://docs.github.com/en/get-started/using-github/github-flow

## 第 4 页
建议用时：55 秒

页面高亮、操作录制和教程管理，已有值得复用的项目。Driver.js 可以作为高亮与提示气泡的基础，OnTheWay 的示范转教程流程、Usertour 的编辑发布和维护机制，也给我们提供了参考。我们的切入点是围绕一次具体任务，把这些能力和当前页面、用户进度、实际结果接起来。比如用户已经建好分支，就从合适的位置继续；选错分支，要提醒修正；PR 建立后，还要核对它是不是这次任务的结果。这也把下一页的需求串起来了。

材料来源：docs/course/week10/调研报告.md §4–6；docs/course/week10/发起人体验记录.md；research/sources.json；research/notes/源码阅读索引.md。上述为本项目产品定位与设计目标；未据此声称参照项目缺乏这些能力。

## 第 5 页
建议用时：55 秒

因此，我们提炼了三项相互配合的需求。定位要跟着页面和实际进度更新；解释要知道用户正在做哪一步，答疑时不用重新交代整段经历；核对则要看操作后的实际结果，比如分支选错了、修改还没有提交，就指出问题，帮助用户继续。它们共同服务于同一件事：帮助用户完成眼前的任务。这些行为已整理为用户故事，并配有具体的验收条件。接下来直接看这些需求如何呈现在用户当前的页面上。

材料来源：docs/course/week10/用户故事.md；docs/requirements/WebGuideAI-SRS-v0.2.md，重点 US03–US06。

## 第 6 页
建议用时：90 秒

假设现在进行到认领任务。左侧就是用户正在用的网页，高亮框指向 assign yourself；右侧说明当前步骤，解释为什么要认领，并显示规则检查还在等待认领结果。如果用户不理解，可以在同一个侧栏继续问 AI，不用离开当前任务去组织一遍问题。用户仍然自己操作网页，规则根据页面结果更新进度，AI 负责解释和答疑。比如认领任务这一步，点击之后还要读取指派结果，包含当前用户时才确认完成。页面变化或者目标失效时，需要先撤掉旧高亮，再重新核对位置。后续的分支、文档提交和 PR 检查也沿用这种交互，首版先带用户走到正确的 PR 已建立，再交给同伴评审。

材料来源：docs/design/WebGuideAI-核心设计-v0.1.md；docs/design/WebGuideAI-工程配置与开发方式-v0.1.md；docs/design/WebGuideAI-引导交互-v0.1.md；docs/course/week10/用户故事.md；docs/requirements/WebGuideAI-SRS-v0.2.md US03–US05。概念原型。

## 第 7 页
建议用时：75 秒

前面的例子，展示的是学习者如何使用一份教程。完整系统还要回答：这份教程从哪里来，页面变了又由谁修。作者可以先录制一次示范，或者依据资料形成草稿，再补齐步骤、适用前提和完成条件。经过目标页面验证后，发布一个可用版本。学习者使用时，如果卡住了，可以反馈到维护环节，由作者修订，或者撤下已经失效的教程。所以 GitHub 协作是我们先打通的一份教程，后面还会建设教程创建、发布和维护能力，让经验可以反复使用。

材料来源：docs/course/week10/用户故事.md；docs/requirements/WebGuideAI-SRS-v0.2.md US07–US13；docs/design/WebGuideAI-核心设计-v0.1.md；docs/design/WebGuideAI-工程配置与开发方式-v0.1.md §1–6。

## 第 8 页
建议用时：65 秒

最后，这套方案怎样落地？浏览器扩展负责眼前页面的观察、任务进度、规则检查和高亮，让交互及时响应；后端统一接入模型，随后承接教程与反馈管理。技术方向是扩展端 WXT、React、TypeScript，后端 Node.js 和 Fastify。我们已经做过页面状态读取、跨页关联和扩展生命周期的基础实验。下一步会把这些机制接到 GitHub 协作的真实页面，先交付一条可用的任务引导，再请新手试走，根据实际卡点修订。后续沿用同一套教程结构，继续建设创建和维护能力。我们希望最终让使用者在当前网页上知道该做什么，也知道自己是否做成。
