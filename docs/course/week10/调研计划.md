## 后续怎样取得更有价值的反馈

- 原型可操作后，优先找 1–2 位没有完成过该 GitHub 协作流程的用户试用，观察找入口、理解步骤、判断提交与交接的困难；这是建议样本，不是统计代表性保证。
- 若作者需求或授权意愿影响当前决策，再进行 15–20 分钟定向访谈；维护者访谈可与教程创建增量一起安排。
- 记录实际任务、初始条件、尝试、结果、必要原话与反例。重点检验高亮是否有帮助、是否需要概念解释、是否愿意在限定范围授权、现有办法是否已经足够。
- 邀请和执行由真人完成；记录参与同意，公开前脱敏。没有回答的内容写未知，AI 不填造访谈与试用结果。

## 可选工作包池

| 工作包 | 保留的产物与验收 | 当前安排 |
| --- | --- | --- |
| A 新手访谈 | 真实匿名纪要，原话与推论分开，3–5 条发现或反例 | 暂缓，后续按试用需要安排 |
| B 熟练用户访谈 | 同上，包含真实答疑／教程维护经历；无经历则写明 | 暂缓，后续按作者增量需要安排 |
| C 公开来源复核 | 核对 5 个原始来源，记录具体支持、差异和不可读取项 | 可选，不立即分派；本轮未代完成独立来源核查 |
| D 故事与讲稿核读 | 逐项检查角色、验收、范围和证据，不要求凑缺陷 | 本轮已有 AI 一致性检查；真人集中核读后续安排 |

四包是可选择的分工形式，不要求每人现在领取一包，也不要求为任务数量拆 PR。需要他人参与时再限定产物与工作量；朋友不默认承担更重的模块，所有贡献按真实执行记录。

报告与故事核读完成后可以进入 PR 评审；当前 main 保护仍需另一位成员真实批准。访谈延期不等于已完成，也不等于已经获得教师对课程提交方式的认可。
