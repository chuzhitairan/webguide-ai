## 3. 第 16 周以后到答辩的任务

资料写明，第 16 周课后继续自主迭代，教师与助教线上巡查仓库：

1. 编码开发：课外约 50 学时。
2. 测试、评审与迭代：约 40 学时。
3. 发布与部署：约 10 学时。
4. 最终答辩：线上线下结合，每组 20 分钟，其中功能与非功能演示 12 分钟、问答 8 分钟；每人至少回答一问。

这三项学时按原文保留；资料未在此明确是按每人还是按小组统计，不能直接换算为整个小组只有 100 人时。答辩日、最终材料提交日、提交入口均待教师通知。

第 16 周的可运行版本宜作为第一个功能切片，而最终交付还需要满足至少 3 个可交付增量、至少 2 轮完整迭代等要求。不能只发布一次原型就结束。来源：S1 第 2 页；S2 第 4 页；S3 第 2–4 页；S11。

## 5. 全程持续做的工程任务

- 每项需求、缺陷、任务先建立 Issue，再开分支和关联 PR；需求变更走申请、评审和批准/关闭流程。
- 初始化 Projects 看板、Issue/PR 模板及 Milestone；README 包含项目章程和过程模型选型论证。
- main 禁止直接推送，PR 至少 1 位成员 Review 通过再合并；CI 红灯不能合并。
- Actions 自动构建和测试，配置自动部署；每个增量打 Release。
- 模型源文件随版本入库，原文要求每张图一个 PR；维护需求 → 用例 → 模型/设计 → 测试的追溯关系。
- 提交和评审应随项目推进分布，不能最后集中打包；若 GitHub 不稳定，按教师认可的 GitLab/Gitee 镜像预案保证每周至少推送一次。
- 从第一周开始记录 AI 工具、用途、参与比例、人的检查方式、修改/拒绝案例；不要到答辩前回忆补造证据。
- 提前轮流安排课堂主讲和评审，持续检查每人的贡献和已合并 PR 数。

来源：S2 第 1、4 页；S3 第 3–5、7 页；S12 第 2–3 页。

## 7. 成绩权重与必须重视的条件

| 板块 | 占总成绩 |
| --- | ---: |
| 课堂讲解与研讨 | 10% |
| 八次阶段检查点 | 20% |
| GitHub 工程过程 | 10% |
| 完整文档链 | 25% |
| 功能与非功能演示 | 20% |
| 答辩问答 | 15% |
| 合计 | 100% |

前 3 项为过程性 40%，后 3 项为期末 60%。应使用版本 2 的权重，不要把迁移对照表中的旧版权重重复相加。来源：S3 第 6 页；S2 第 4 页。

教师明确写明：课前材料不齐会取消当次讲解资格并计入过程成绩；每人都要能解释负责内容。版本 2 还列明系统不能运行且无合理解释、文档代码明显不符、被点名成员讲不清内容、AI 未声明等答辩红线。班级要求另列买卖代码/代做、伪造记录、AI 冒充人工关键决策等不及格情形，并将缺勤不少于 3 次列入不及格档。来源：S2 第 2、5 页；S3 第 6 页。

AI 可以辅助竞品调研、整理材料、界面和样板代码、测试草稿与文档润色；真人访谈、需求确认、架构与接口定稿、验收放行等必须由人完成。核心算法与关键模块也要求成员能够讲清自己完成的代码；模型语法与一致性需掌握，并能手工绘制。具体边界依 S3 第 5 页表格执行。

选做加分：课程期间向 Star ≥ 100 的公开开源原始仓库提交并被合并的 PR，文档类 +2、代码类 +3，累计封顶 +5，计入过程性 GitHub 部分；不能是自己或组员的 Fork，答辩需提供 Merged 链接并解释内容和动机。下载、阅读或仅提交未合并的 PR 不满足这一条件。来源：S3 第 6 页；S2 第 5 页；S4、S11。

## 8. 对 WebGuide AI 的直接影响与建议

以下是项目建议，不是教师新增加的要求：

1. 产品用户可定义为“学习者、教程作者、平台管理员”，据此明确三种角色与权限；它们与项目经理、开发、测试等团队岗位不同。
2. 将三个增量规划为：v0.1 手工教程＋网页引导闭环；v0.2 操作录制＋教程编辑/版本管理；v0.3 文档生成＋有限纠偏＋反馈统计。每个版本都应能演示实际用户任务。
3. 外部集成优先选择明确列举的 GitHub OAuth 登录。当前资料没有明确确认“调用大模型 API”可替代该项，可向老师确认后再决定；不能自行视为已满足。
4. 风险点可选择“动态页面目标定位与纠偏可靠性”，记录原型、失败条件、缓解方案和测试结果。
5. 真人调研面向实际新手、会录制教程的熟练用户，以及负责维护教程的人。现有竞品源码研究能支持调研，但不能代替真人访谈和用户确认。
6. 第一轮优先形成可验证的引导功能切片；后续增量逐步加入录制和 AI。编程原型可以支持前期决策，但不能代替需求和设计材料的正式评审。
7. 本次资料补充了 4–5 人、文档链、建模与个人贡献要求；此前以 3 人计算的工期只是估算示例，之后排期应按实际组员与这些交付要求重算。
