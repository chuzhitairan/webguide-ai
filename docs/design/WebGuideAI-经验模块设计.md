# WebGuide AI 经验模块设计

2026-11-24 · 评审稿

经验模块帮助 Harness 少走重复的弯路。比如模型知道维基百科的正文字号通常在外观面板的 Text 区，就可以优先观察那里。它仍要结合用户原话找对控件，并从当前页面确认选择生效。

最近两次固定面板复测中，找到字号选项的那次已经能够在点击后直接收尾，另一次仍停在初次定位。首轮经验实验就从这个可区分的问题开始，再用 Figma 检查同一套办法能否复用。[维基百科验证](导航Harness-真实站点验证-2026-11-23.md#操作后优先复查)

## 1. 从其他做法借鉴什么

| 做法 | 对 WebGuide AI 的启发 |
| --- | --- |
| Agent Workflow Memory 从操作记录提炼可复用的局部流程，按任务提供给模型。论文也观察到，模型有时会过度遵循旧流程。 | 提炼「满足什么条件时先看哪里」，让模型用现场确认适用性。换起点和页面状态时，可以采用同一条经验中的一部分。 [论文 §2](https://arxiv.org/html/2409.07429#S2) · [论文 §3.2](https://arxiv.org/html/2409.07429#S3.SS2) |
| ExpeL 对比同一任务的成功和失败，从不同任务中找共同做法，再用未见过的任务评估。 | 提炼时同时看走通和走偏的记录。用另一组页面状态和说法验证，避免把记住旧用例当成复用收益。 [论文 §4.2](https://arxiv.org/html/2308.10144#S4.SS2) |

首轮建议采用**版本化的短线索**。整段会话能保留丰富的历史细节，适合离线复盘。固定流程适合需要统一操作顺序的练习。短线索可以适应用户自行换路，也容易比较模型究竟少做了哪一次补看。

## 2. 一条经验长什么样

每条经验尽量解决**一个可以复用的导航判断**。记录让下一次引导能找到适用线索，也让维护者能查回原来的证据。

| 字段 | 作用 | 维基百科示例 |
| --- | --- | --- |
| 标识和修订号 | 知道使用了哪一条、哪个版本。修改内容时保留标识，增加修订号。 | `wikipedia.text-size`，第 1 版 |
| 站点和目标 | 站点用主机名，目标用简短自然语言描述。 | `en.wikipedia.org`，调整文章正文字号 |
| 适用情境 | 模型需要从当前页面判断的前提。 | 桌面文章页，有 Appearance 外观入口或面板 |
| 建议和例外 | 建议优先查看哪里，以及布局变化时怎么继续。 | 优先查看 Appearance 的 Text 区。面板已展开就读该区，收起时先找外观按钮。 |
| 核对信号 | 提醒模型到现场看什么。 | 在 Text 区核对用户要求的字号选项是否已选中 |
| 来源和状态 | 留下验证记录、最近验证日期和当前状态。 | 固定面板与收起菜单的试跑记录，待对照 |

控件临时编号由当前观察产生。写经验时保留可复用的控件名称和位置关系，项目名称、具体页面地址和临时编号留在原试验记录里。运行时给模型的摘要包含目标、适用情境、建议和核对信号。条目状态用「候选」「可用」「停用」表示。来源可以是试验编号、仓库中的复盘文档，或获准保存的本地记录编号。

## 3. 经验如何产生、更新和停用

1. **从已有试跑提炼候选。** 首批取维基百科字号和 Figma 导出入口。一起看走通与失败时模型看到的内容，并区分实际到达、误指、收尾漏判和模型请求失败。比如输出截断属于调用故障，不能单凭这次失败推断网站的入口规则。
2. **复查候选。** 首批由维护者整理，按目标与页面条件合并重复条目，再用未参与提炼的用例回放。试验开关只载入本批指定的候选，整批使用同一目录版本。试验通过后，将有收益的条目标为试用版可用。
3. **使用后记录结果。** 实验日志记本轮提供了哪些条目、是否指对和是否完成。结合模型实际提出的查找范围判断经验有没有影响决策，无法判断就记为不确定。实际结果以页面核对或用户确认为准。
4. **发现冲突就复查。** 页面明确与线索不符时，本轮按现场继续。维护者可以停用条目，或发布修订版并留下原因。个别会话未找到控件时，先保留观察结果，等区分是页面改动、采集遗漏还是经验不适用再处理。

多站反复出现的现象进入工程复盘。比如「操作后优先复查刚高亮的控件」已经由维基百科案例提出并通过通用回归。类似发现可以形成下一条 Harness 改进建议，经独立验证后进入代码。

首轮取材于公开网页和练习稿。若随后从用户的本地试用会话提炼，是否保留试验记录由用户决定。模型调用收到的是已裁剪的当前观察和少量经验摘要，目录里保留的来源与试验统计用于维护。

## 4. 经验怎样进入导航循环

1. **先拿到当前页面。** 扩展取得授权后，沿用首读与补看协议。现有本机服务按观察中的主机名读候选，从首个模型请求开始提供该站点的摘要。第一阶段目录很小，每次最多给 5 条，模型用原目标和现场状态判断相关性。切到另一个已授权站点时，按新主机名读取候选。
2. **给模型同一轮的三项输入。** 用户原话决定终点，当前观察提供事实与临时控件编号，经验补充可能的查找方向。经验作为单独的数据字段随现有请求发送，沿用当前的请求和补看预算。实验两组使用相同的模型指令，有经验组带候选，无经验组带空列表。
3. **由现场决定下一步。** 条件吻合时，模型可直接选取当前控件，或优先补看经验指向的区域。条件还不明确时，可以用当前预算补看。现场与经验冲突，或用户改变目标时，依当前目标和页面重新判断。
4. **完成沿用现有核对。** 高亮只能引用本轮控件。找到入口时核对正确控件，状态生效时核对当前选项或结果，网页外结果继续由用户确认。以 Figma 为例，找到导出入口可以在指对按钮后收尾，用户要确认电脑上有 PNG 时仍需要确认下载。

目录缺失、暂时停用或没有适用经验时，服务按无经验模式照常引导。每轮备选的顺序和数量可从试验记录重建。更多条目带来的遗漏或冲突可以用数据量化，再判断是否需要更细的检索。

## 5. 怎样存，谁负责读写

| 阶段 | 存储和所有权 | 何时推进 |
| --- | --- | --- |
| 对照实验 | 仓库中一份版本化 JSON 保存审核过的试验条目，本机服务读取。来源记录和结果单独保存，运行期只读目录。 | 第一步落地。用 Git 复查差异和回退，用目录版本重跑结果。 |
| 单机试用 | 从试验目录导入初始条目，之后以扩展的本地持久存储为准。用户能查看、关闭和删除经验，侧栏在请求时传递筛出的摘要。 | 对照显示有收益后接入。继续沿用同一字段和查询规则。 [Chrome 扩展本地存储](https://developer.chrome.com/docs/extensions/reference/api/storage#storage-areas) |
| 小组共用 | 先用 Git 管理一份共享目录，由维护者评审并发布版本。 | 几个组员只需要读同一份经验时即可采用。 |
| 云端协作 | 服务管理候选、验证记录和发布版本，并控制谁可以贡献、试用和发布。发布时核对修订号，客户端读取有有效期的目录，可切回上一可用版本。 | 出现跨设备同步、多人在线维护或共享积累需求后，按下方上线方案设计接口和数据库。 |

目录有一个格式版本，每条经验有稳定标识与修订号。实验记录另存引导构建、模型配置、目录版本和实际提供的条目及修订号。切换存储时复用「按站点读取可用候选」这一个入口。何时需要编辑、停用和发布分别由上表的阶段决定。在团队阶段之前，存储层的选择主要看是否便于复现、查看和回退。

## 6. 首轮验收怎样做

本机开关和两条候选已经接入。真实维基百科和 Figma 固定页面的对照见[首轮经验对照](导航Harness-经验对照-2026-11-24.md)。

首轮先看有经验时能否让更多用户正确到达目标，并让扩展在证据足够时正确收尾。再比较找路耗时和补看次数。遇到过时或不适用的经验时，检查模型能否根据现场继续走对。

| 用例 | 验证点 |
| --- | --- |
| 维基百科固定外观面板，换一种说法要求调大正文 | 正确找到 Text 区的目标单选项，独立核对选中状态和正文字号，再检查侧栏收尾。 |
| Figma 换起点找图层的图片导出入口 | 选对图层，最终指到实际导出控件。分别从已选中和未选中起步，并保留页面级同名入口作为干扰。 |
| 回放中过时的经验指向错误区域 | 保留旧区域及同名控件作干扰，把目标放到另一个区域。核对模型能否根据控件状态和所在区域换路。 |
| 回放中目标超出经验覆盖 | 用户要求确认 PNG 已下载，试验经验只覆盖找到导出按钮。核对模型能否保留真实终点，并在需要时请用户确认。 |

先用固定页面观察做回放，确认经验字段进入了预期请求、错误线索也能让位于现场。再挑维基百科和 Figma 各一个真实起点，固定模型、目标、页面起点和预算，交错跑有经验与无经验，每组各重复两次。两种模式都使用提炼经验时没有用过的说法或起点。

分别记录实际到达、正确收尾和错误指引，再比较首次正确高亮耗时、补看次数与模型调用次数。模型服务失败单独记录。有经验时若能重复提高到达率或正确收尾率，且没有增加误指或误报完成，就有继续投入的理由，即使调用和等待相近。若两组完成表现相近，稳定减少等待或补看也是收益。成功率和等待时间同时上升时，结合用户多等多久、多少次失败因此变成成功来判断。小样本先用来找值得复验的信号，下一轮优先覆盖无经验时容易走偏、又能从现场核对终点的起点。

## 7. 实施顺序

1. 从已有验证记录写出两条候选，定好来源、适用状态和最小数据格式。
2. 用本机服务读固定目录，加入有经验与无经验的试验开关，保留现有扩展的引导和收尾协议。
3. 按验收表跑回放和真实站点对照，据结果决定单机持久存储与候选提炼是否进入下一版。
4. 若对照显示收益，用已有练习记录试跑自动提炼。将模型生成的候选与维护者写的条目一起放进未见用例，检查它能否找出有效条件、保留反例、避免把未知结果当成功。之后再用团队内测验证共享、停用和回退。

## 8. 上线后怎样自动积累经验

上线后的目标是**让模型自动整理候选，让证据决定它能用到多大范围**。用户照常操作。候选生成、去重、验证和发布在会话后运行，当前会话继续使用已发布的目录。ExpeL 提供了从成功与失败的对比中提炼经验的做法，Agent Workflow Memory 的在线实验也观察到错误轨迹会污染后续指引。下面的发布流程针对这个问题设计。[ExpeL §4.2](https://arxiv.org/html/2308.10144#S4.SS2) · [Agent Workflow Memory §3.2](https://arxiv.org/html/2409.07429#S3.SS2)

### 从用户操作中留下证据

用户可分别开启本机积累和共享贡献，两项默认关闭。扩展只在引导会话和已授权页面内，保留目标、实际展示的指引、用户实际操作的控件摘要、操作前后的关键状态和结果。结束后清理原始观察，只留下提炼所需的短记录。提交共享时，上传的是用户授权的最小化样本，例如泛化目标、控件角色、公开界面标签、状态变化和结果类型。项目名、原始网址、表单值等在本机裁掉。无法判断一段内容是否适合共享时，留在本机。用户可查看和撤回贡献，服务按来源查找受影响的候选和已发布条目，重新核对剩余证据。

同一会话里，「模型指了哪里」「用户实际点了哪里」「页面有什么变化」分别记录。比如模型没找到维基百科的字号控件，用户自己点了 Text 区的 Large，扩展之后确认 Large 已选中。这个样本说明用户找到了有效入口，也说明当时的指引没帮上忙。若用户只是关闭侧栏，结果记为未知。用户中途换目标时，新目标单独记录。

| 结果信号 | 候选提炼时怎么用 |
| --- | --- |
| 页面有可核对的终点 | 用作成功证据。根据用户原目标核对对象和结果，例如正确图层的导出入口、指定字号已选中。 |
| 用户确认网页外的结果 | 记录为用户确认，例如文件确实下载到了电脑。可以帮助提炼前面的界面线索，共享发布仍要独立复现相关控件及适用条件。 |
| 明确指错、操作未生效或用户纠正了指引 | 和同目标的成功样本对比，找出哪条建议应补条件。网络超时、页面漏读等原因另记。 |
| 证据不足 | 留作待观察样本。停止、离开、点击或模型报告完成本身，都不能给经验增加一条成功记录。 |

### 自动提炼、合并和更新

1. **归组。** 用站点、目标类型和起始状态寻找相似记录。模型可把「字号太小」和「把正文调大」归到同一目标。对已经报告过的会话去重，避免上传重试或同一人的重复试跑抬高支持数。
2. **找差异。** 总结成功案例中帮助找到目标的那一步，再用失败或绕路记录找适用条件。模型给出新建、补充例外、合并或停用的建议，并引用支持和反对的证据。每条经验保留目标、页面条件、建议和核对信号，引用仅用于复查来源。
3. **按条件整理。** 同一入口在相同状态下的重复样本归到一条。不同起点各自走通时保留分支，例如「外观面板固定」和「外观面板收起」。相同条件下仍有冲突就保留证据等待复验。新版本通过验证后才替换已发布版本。

### 让发布、监控和回退自动运行

| 阶段 | 自动处理方式 |
| --- | --- |
| 候选 | 校验条目字段、来源、适用范围和数据是否可共享。模型生成的是草稿，发布流程只接受通过校验的版本。 |
| 独立验证 | 用未参与提炼的用例测试每个要发布的页面变体，并加入会使经验失效的反例。回放检验模型能否选择或放下经验，独立的当前页面试跑确认入口仍有效。验证用页面或用户证据判断结果，避免由起草模型给自己打分。 |
| 小范围试用 | 低风险、终点可核对的条目通过验证后，可自动给少量参与试用的会话使用。同类会话按相同起点条件分组，对照上一版本或无经验。记录条目修订号、是否提供、用户结果和指引耗时，区分用户绕过提示后的成功。 |
| 发布与停用 | 有足够的对照样本、达到第 6 节的收益条件且指错和误报完成未增加时，再扩大范围。没有足够样本就维持试用。上线后若用户频繁换路或找不到目标，触发复验。复验发现经验失效时自动暂停，换回上一可用版本或无经验。目录有有效期，让暂时离线的客户端也能停止使用过期经验。 |

维护者设定发布条件、处理证据冲突并抽查已发布的经验。内测可先让维护者确认发布，再用复验和回退记录决定哪些低风险条目可以自动放行，以及样本量和异常停用阈值。跨站反复出现的观察缺口由系统汇总成 Harness 改进建议，进入已有的回归验证流程。

共享服务将贡献记录、候选和发布目录分别保存。每次提交可去重，每次发布有版本和回退入口。贡献积累和检索彼此独立，验证和整理在后台完成，导航请求只读适用的已发布摘要。
