## 滚动后重新观察

用独立的浏览器回归复现了一个可解释的断点。用户滚动后，目标虽然进入视口，首读仍被更靠前的控件占满。模型只给了滚动文字、没有提供区域编号时，旧扩展没有开启新一轮。修正后，文字提示会等一次实际滚动触发重新观察。有区域编号时仍优先关注指定区域。[浏览器回归](../../tests/e2e/guide.spec.ts)

首轮固定页面的脚本没有记录实际滚动位置。有一次补测发现驱动发出了滚轮输入，但面板位置仍为 0，这些试次不能用来判定扩展是否接到滚动。在修正后的 Figma 固定页面，有／无经验各一次明确观测到属性面板从顶部滚到 1595px。模型均返回了区域编号，两组滚动后都收到新一轮观察，高亮了正确按钮并完成收尾。

## 同名入口补测

在固定页面把页面级导出与 Frame 1 的导出按钮都命名为 `Add export settings`，分别放在不同区域。终点以实际高亮的位置为准，同时单独记录侧栏是否正确收尾。用同济模型和同一目标试跑。两处入口都在视口时，结果如下。

| 模式 | 指对图层入口 | 正确收尾 | 因截断或超时无可用回复 |
| --- | ---: | ---: | ---: |
| 无经验 | 1/4 | 0/4 | 3/4 |
| 有经验 | 2/4 | 1/4 | 2/4 |

有可用回复的三次都指对了，其中一次正确收尾。两组的故障次数不同，样本也少，暂时只能把收尾改善当作初步信号。

另从图层导出按钮仍在视口外的起点各跑一次。两组都指到了可见的页面级同名按钮，无经验组还报告完成。这暴露了一个独立问题。核对按钮名称和选中图层的状态，仍需验证按钮确实属于该图层。

## 同名入口的归属核对

浏览器回归用相同名称的两个按钮重现了旧版误报。先给出页面级按钮及另一处属性面板的名称，旧版会把两条分别成立的证据当成完成。只修改完成验证后的模型试跑仍出现过普通高亮指错。现在扩展在普通高亮和完成时都比对已渲染的同名可用控件，并检查引用的区域能否包含目标并排除其他候选。`inspect` 返回几层上级区域，便于模型找出区别。回归验证前述两类误指被拦下，以及滚动后能指对并正确收尾。[浏览器回归](../../tests/e2e/guide.spec.ts)

页面脚本检测到同名控件时，还要求至少另一个候选进入模型本轮的观察或补看。同济模型在固定页面用两种经验设置各跑一次。无经验时，补看后提示滚动并正确高亮，未自动收尾。有经验时，模型曾把页面级的 `Page export` 当成图层入口并提交完成证明。扩展没有显示这个高亮，随后模型补看并提示滚动，滚动后两次输出截断。这两次试跑都没有误高亮或误报完成。实际指路和收尾仍分别记录。

## 提高单次生成额度

试验阶段把每次生成上限由 1,024 提到 4,096 tokens。思考和最后的 JSON 指令共用生成额度。用同济模型对三个固定观察各比较一次，按浏览器的 15 秒单次等待上限计时。

| 固定观察 | 1,024 tokens | 4,096 tokens |
| --- | --- | --- |
| 同名导出入口 | 8.3 秒，达到上限，JSON 被截断 | 6.0 秒，返回通过格式和证据编号核对的高亮指令 |
| 多项完成条件复核 | 14.0 秒，1,024 个全用于思考 | 15 秒内未返回，探测到期 |
| 仓库活动筛选 | 8.7 秒，1,024 个全用于思考 | 14.6 秒，生成 1,903 个 token，返回通过格式和证据编号核对的高亮指令 |

多项完成条件用 4,096 tokens 并行复跑三次，32 秒内都未拿到响应。复查发现这组探针同时指定了 `reviewRequirements: true` 和需要用户确认的 `user` 条件。它直接调用了模型，正式引导接口会在调用模型前拒绝这类输入，因此上表对应一行和 32 秒记录仅描述该探针。提高生成上限让部分较长的判断可以完整返回。上述结果是固定观察的单请求验证，端到端到达和收尾沿用各自的验收记录。

## 网页完成条件复核

用接口实际接受的输入串行复测。需要合并的筛选条件在原提示下两次给出正确的归并和证明，耗时 13.5 秒和 6.7 秒。单独提供已通过和未通过的下标，一次在 10.7 秒后正确归并，一次等到 15 秒。缩短提示或关闭推理能更快返回，也出现了把已生效的筛选继续当作下一步的情况。两项独立结果的用例同样出现了快慢波动。

网页重新观察后，浏览器现在会再核对之前通过的证明，向模型列出当前已通过和待核对的项目。仍有效的证明可以继续参与收尾。模型如果归并了完成条件，则按新的下标重新取证。新增会话回归覆盖了两种情况。模型只补交剩余项即可正确收尾，旧证据已经失效时则保留未完成状态。这个改动减少重复提交证明，模型单次耗时还受每次推理影响。[会话回归](../../apps/extension/src/guide/__tests__/session.test.ts)

## 最新构建的固定页面对照

固定扩展和 API 代码，以仓库提交 `ce6fa3d` 为产品基线。模型使用同济 `DeepSeek-V4.1-Flash`，每次生成额度 4,096 tokens，浏览器单次最多等 15 秒。每个起点做三对串行试跑，交替有、无经验先后顺序。两组使用同一任务「我想把 Frame 1 导出成图片，先帮我找到它的导出设置入口。」开启组使用 `pilot-1` 中的图层导出经验。

固定页保留页面级的同名按钮。Frame 1 未选中时，图层属性面板隐藏；已选中起点的属性面板可见，正确的导出按钮在视口外。脚本只跟随已显示的选择或滚动指引，并确认滚动实际发生。正确到达以浏览器高亮 `frame-export` 为准，正确收尾还要求侧栏显示完成且最后高亮的是这个按钮。页面级按钮和 Cover 的高亮记为误指。模型提出补看、引导请求、服务错误和等待时间一起记录。固定页用于对照引导能力，真实 Figma 编辑器仍有单独的验证记录。[固定页与判定](../../experiments/experience-comparison/figma-export.spec.ts)

## 收尾证据追踪

固定页脚本现在记录模型提交的完成条件数、证明数，以及服务转给扩展的条件类型和证明数。首次观测到正确高亮时，脚本保存当时最近一次被服务接受的请求及其序号，供回放使用。

从「已选中，按钮在屏外」复跑有、无经验各一次。两次都提交了有效的「找到入口」条件和证明，服务转交后，扩展都正确高亮并结束。含滚动前的请求，两次分别用 32.7 秒和 21.9 秒。

保存两次滚动后的页面观察，用同一模型和请求校验回放。现有提示词共跑 6 次，均指对按钮，3 次有有效的完成证明。其余 3 次中，1 次没有提交证明，2 次提交的证明没有可引用的有效条件。其中一次的 `quote` 只摘了「找到它的导出设置入口」。接口要求条件中的引文合起来覆盖用户原话，以免复合目标漏掉一项，因此接口没有将这份证明转给扩展，普通高亮仍然有效。原先 4 次未收尾没有逐条记录，无法逐次归因。

另外试了两版提示词。第一版强调「先找入口」以指到入口为终点，4 次都没有交出有效证明。第二版进一步要求 `requirements` 为空时用整句原话建立 `point` 条件，并在同一回复提交序号为 0 的 `proof`，2 次都过了接口校验。这个回放只覆盖同一个目标，两版均未纳入正式提示词。

## 三类目标的收尾对照

把候选提示改成通用规则。还没有完成条件、页面已经有结果证据时，在同一条回复里提交完整的完成条件和已有证明。只有一个结果时引用完整原话，有多个独立结果时保留每项，只提交当前证据能支持的证明。

使用 5 份固定观察。Figma 保留两个同名入口，检查是否证明了属于 Frame 1 的入口。GitHub 分别呈现 Issue 链接和实际详情，检查「打开」是否要等到详情可用。维基百科分别呈现字号已生效、主题未生效，以及两个设置都已生效，检查两项是否各有证据。每份观察都由正式接口校验格式，经验关闭。同一模型、生成额度和 15 秒等待限制下，两版各跑两轮，交替先后顺序。实验只测模型和接口能否给出与当前页面相符的证据，最终高亮与侧栏状态由浏览器试跑验证。[回放脚本](../../experiments/experience-comparison/completion-replay.mjs)

候选版的两次 GitHub 详情请求中，一次只核对了标题，一次仅引用用户目标的一部分，证明没通过接口。入口可见时，现行版还曾把「打开 Issue」存为「找到入口」。在只完成一项的复合任务里，现行版有一次保住已完成项的证明，候选版两次都没把这份证明交到扩展。其中一次模型拆对了两项，还提交了字号的证明，但引用片段跳过了「并」字，接口因此丢弃了条件和证明。

候选句暂不纳入正式提示词。样本里的收益集中在入口和两项都已经完成的画面。工程上应优先保证完成条件的提取、保存与网页验证三个环节各自可诊断，尤其要区分目标类型判断错误和原话引文缺失，才能纠正已经存错的条件或找回被丢掉的有效证明。

## 最终指引

此前模型可能只返回普通高亮，将「此控件就是终点」和控件证明漏掉。新决定 `point` 只需要引用当前控件和必要的所属区域，本机服务用当前观察生成入口证明，沿用浏览器原有的可见性、可用性和同名控件归属核对。已有多项结果时，决定需要给出这一入口对应的下标。到达界面和设置生效仍各自核对页面状态。

同济模型回放保留先前五份观察，另用同一个 GitHub Issue 列表验证「找到入口」与「打开 Issue」两种表达，每份各跑两次。

