# 第二阶段技术约束核对

日期：2026-11-16。状态：总体方案比较前的设计输入。输入：[已确认首版范围](../requirements/第一阶段范围评审记录-2026-11-16.md)。

## 1. 已核对的浏览器机制

| 机制 | 官方资料支持的事实 | 对本项目设计的影响（助手判断） |
| --- | --- | --- |
| 内容脚本 | 可读取、修改网页 DOM，并与扩展其他部分通信；执行环境与网页脚本隔离 | 页面目标定位、高亮和必要观察可在网页侧实现；状态协调与模型请求不必全部放在内容脚本中 |
| activeTab | 用户激活后授予当前标签页的临时访问；同源导航可以保留授权，跨源导航或关闭标签页会撤销。不能概括为“换页／刷新就失效” | 授权是否有效与新文档是否已有内容脚本是两件事。全程引导需处理新页面注入与恢复，跨 GitHub 和站点需处理授权边界；activeTab 本身不排斥页面内高亮 |
| 站点授权与内容脚本 | 可声明主机权限，也可在运行时请求已声明的可选主机权限；内容脚本支持静态、动态注册或程序化注入 | 比较按任务请求实际目标主机、注册内容脚本的方案；不能把授权、脚本注入和任务开关混为一个配置 |
| Edge sidePanel | 微软支持列表列出桌面 MV3 的 sidePanel API | 可作为答疑和进度界面候选；网页高亮仍由网页侧实现，使用侧边栏不是全程高亮的必要条件 |
| 侧栏关闭与连接信号（2026-11-17 补核） | Chrome 官方已列出 sidePanel.onClosed，标注 Chrome 142+；Port.onDisconnect 有端点卸载、导航、主动断开等多种原因，仅打开端口不保证后台常驻 | 当前 Edge 的事件能力和行为需实测；按实例／窗口／任务关联信号，不能直接认定断开等于用户关闭。侧栏和页内面板仍为候选 |
| 扩展 service worker | 可能因空闲等条件终止，全局变量随终止丢失；官方建议使用存储保存状态 | 会话恢复不能只依赖常驻内存；需要定义状态保存、页面身份和过期证据恢复规则 |
| Edge 兼容 | 微软说明 Chrome 扩展可迁移，但要求检查 Edge 支持的 API 并实际测试 | Chrome 官方资料用于机制参考；首版仍须对使用到的 API 在 Edge 中核对，不能以文档兼容推定已测试通过 |

## 3. 总体方案比较前的共同条件

- 用户执行网站动作，扩展负责可视指引与观察；模型不能覆盖规则完成状态。
- 当前步骤的定位、高亮和固定说明应能够在模型暂不可用时继续提供。
- 模型请求只携带必要任务上下文，具体字段、凭据和接口在设计中定义。
- 首版恢复范围为同一浏览器会话；页面、目标和观察有效性必须重新核对。
- 后续教程编辑与维护需要复用首版的步骤、目标和规则表示，避免出现两套互不相容的格式。

接下来比较本地扩展与后端的职责分配，再形成正式设计。技术栈、数据库、模型提供方和发布方式尚未确定。

## 4. 用户转交 Gemini 评审后的处理

| 意见 | 核查结论与后续动作 |
| --- | --- |
| 手动 popup 采集不能直接成为最终全程引导 | 采纳交互改造方向，修正 activeTab 的失效描述。设计中分别定义权限、注入、任务开启／暂停、跨页恢复。优先比较任务所需主机的可选授权；目标站点是实际用户的 github.io 主机，不默认授权整个 *.github.io。github.com 主机授权后仍需在应用中限制目标仓库与页面。现有实验保留其读取验证用途，不为本条意见立即扩大权限 |
| Pages 应作为第一份声明式剧本 | 纳入设计比较：少量步骤与条件类型、运行时数据校验、通用流程推进／高亮／证据机制，加 Pages 适配器。站点专用采集可以存在，避免把仓库、步骤顺序与目标版本散落写死在运行引擎。JSON 剧本不等于支持任意网站，更不构成 100% 稳定保证；不建设完整编程语言，也不执行剧本下发的任意 JavaScript |
| 减少重复防御性文案 | 采纳。阶段总结集中保留证据边界；设计正文优先写模块职责、状态图、数据与接口契约、异常和验收对应，避免每节重复免责声明。小改直接回写现有文件，不为每次意见新增一份文档 |
| 缺少真新手验证 | 采纳为后续形成性验证：在交互方案定稿前安排 1–2 位未配置过 Pages 的参与者，用可操作原型和练习材料观察卡点。结构设计与招募可并行；不重开第一阶段或用该数量推导总体成功率。试用前说明评估对象是指引／产品，记录人工帮助与理解反馈 |

上述是评审后的设计约束与待比较方案，总体架构、权限清单及具体 UI 仍需在设计中确定。下一份核心设计应直接交付模块职责、状态机、最小剧本结构、通信消息、权限生命周期及验证安排。

### 本轮 SRS 评审的核查与处理

| 意见 | 纳入设计的要求与修正 |
| --- | --- |
| 自动锚定目标版本 | Q02 增加版本来源、确认时刻、冻结及显式重设；自动读分支提交是候选。不能无提示地拿任意成功 run 自己的提交当作用户预期；先区分核对指定部署与核对最新源修改 |
| SPA 与跨标签导航 | Q04/Q05 覆盖整页和无刷新 URL／DOM 变化、同页／新标签打开站点、并行任务与文档身份。tabs.onUpdated、webNavigation 历史事件及 DOM 监测作为候选组合；单靠 URL 变化不能覆盖 URL 不变的 DOM 替换。实际 GitHub 路径采用何种导航、链接怎样打开应实测，不假定每次相同 |
| 清除旧高亮 | FR04、NFR02、Q07/Q10 明确先撤销失效指示，再异步定位，撤销与新目标显示分开计时；不承诺“毫秒级／零延迟”。仅 AI 解释不使有效定位失效，也不必移除高亮 |
| 轻量任务校验器 | Q03 比较“简单步骤机制＋任务校验器接口”；PagesVerifier 可作为专用实现的候选名称，未固定接口或类名。SRS 不要求 #verification 选择器；它是已有实验的具体采集方式 |

官方文档确认 webNavigation 有历史状态更新事件并携带标签页／文档信息；DOM 内容变化可通过 MutationObserver 观察。选用扩展事件仍需核对权限与 Edge 支持，当前只整理设计约束。
