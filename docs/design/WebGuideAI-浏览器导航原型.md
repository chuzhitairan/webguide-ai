新一轮的页面观察、模型循环和验收设计集中在评审稿。[导航 Harness 设计](WebGuideAI-导航-Harness-设计.md)

## 原型希望用户看到什么

用户打开扩展，说「带我找到这个仓库 README 的编辑入口」。AI 看当前页面，决定该高亮哪个链接、菜单或按钮，以及旁边该提示什么。扩展在网页上显示高亮和气泡，用户自己操作。用户可以从已经打开的 README 开始，也可以在途中自行切换页面，AI 根据眼前的状态重新判断。

早期原型用 GitHub 和 Figma 的预设任务验证视觉引导。下一轮让用户用自然语言提出目标，用预设任务对照之前的表现，再在两个网站上各选一个新任务检验同一套观察和高亮机制。

例如用户点了编辑按钮后，GitHub 显示 Fork 提示。如果用户只想知道编辑入口在哪，扩展可以说明入口已找到，并解释 GitHub 为什么要求 Fork。如果用户想继续进入编辑器，AI 根据页面说明可选路径，由用户决定是否继续。扩展根据当前页面区分已经看到编辑区和还差一步。

## 为什么叫浏览器导航 harness

这里的 harness 是**给 AI 提供网页观察、视觉指引和结果反馈的运行层**。浏览器扩展是它接触网页和用户的地方。模型根据页面选下一步并写提示，扩展把选择变成实际高亮和气泡。用户操作后，扩展把新页面状态交回给模型。换一个站点，按钮和页面会变，观察、定位、高亮和回读这套机制还能接着用。

| 部分 | 在原型里负责什么 |
| --- | --- |
| 浏览器扩展 | 从当前标签页提取标题、可见按钮和链接、所属区域等有用信息，用临时编号表示控件。按 AI 的建议渲染高亮和气泡，观察用户操作后的页面。 |
| AI | 结合用户目标、眼前的控件、上一步结果和相关经验，决定高亮目标和提示。页面跳转后可以调整指引，缺关键条件时可以解释或向用户提问。 |
| 经验库 | 保存一小段可以复用的做法，比如「在文件工具栏找 Edit 入口」，以及它适用的情境、实际结果和来源。 |

先用网页自身的结构来定位。遇到图标名称缺失、页面布局无法从结构理解的场景，再试截图。第一版沿用现有扩展和后端，打通「读页面 → AI 选控件和提示 → 扩展高亮 → 用户操作 → 读结果」这一轮即可。

### 一次引导怎么往下走

下面的提示更新和等待时间来自预设原型，供新设计参考。

1. AI 返回「高亮控件 7，提示『点这里打开文件操作菜单』」。扩展确认控件还在当前页面，然后显示高亮和气泡。
2. 用户自行点击、滚动或切换页面。跳转时立即撤下旧高亮。新页面先合并变化，等约 180 毫秒没有新变化后读取，持续变化时最多等约 650 毫秒。图片等资源可继续加载。
3. AI 根据新状态指下一步。页面已跳转时，过期的控件编号随旧页面失效。到达目标时显示结果，遇到权限提示就解释当前卡点。有多个相似控件、无法确认目标时，先在侧栏提问或请用户选路线。

如果页面只是晚加载了一批控件，原高亮照常显示。扩展挑出与任务有关的变化，把原建议和变化的控件交给模型复核。新增另一条可行路径时沿用原建议。新线索纠正了判断，或让暂行指引有了明确入口时，模型可以换一步并说明原因。目标消失或任务状态变化时，直接按新的页面状态处理。

AI 从第一个提示就参与选路，可以根据用户自己选择的入口接着引导。原型先检验网页高亮和提示能否跟上真实操作。

## AI 怎么把一次引导变成经验

先用一份本地经验表跑通闭环。扩展观察到预期结果后，让 AI 从这段引导里提取候选经验并存到本地。比如下面这条。

| 要记什么 | README 例子 |
| --- | --- |
| 适用情境 | GitHub 仓库内已经打开目标 README，目标是进入该文件的编辑器。 |
| 可尝试的动作 | 在文件工具栏找编辑入口。编辑图标可能单独显示，也可能藏在菜单里。 |
| 结果与例外 | 出现该 README 的编辑区才算进入编辑器。出现 Fork 提示时，记录权限分支及对应提示。 |
| 来源 | 实际引导时看到的页面状态，以及用户操作后出现的结果。 |

下一次，先把相关经验交给 AI，让它结合当前页面决定能否用上。成功复现、判断条件也简单的片段，可以让扩展直接匹配并高亮。遇到页面改版或经验不符，就继续实时找路，回头更新那条经验。失败记录也可以简短保留，帮助识别来回跳同一页面等卡点。官方文档和人的示范都可以作为经验来源，完整固定教程仍然适合需要统一演练的任务。

这轮先回答一个具体问题：**一次引导学到的做法，在另一个起点或另一项相似任务里能不能复用？** 一次成功只是线索。后续复现时看能否减少步骤或模型调用，以及页面稍有变化时能否继续指对。

## 第一轮怎么验证

2026-11-20，指定 Issue 已在独立 Chromium 中接通同济模型。从 VS Code 仓库首页和 Issues 列表分别开始，模型选出页面中已有的链接，测试点击高亮后，扩展用详情页的标题和编号确认到达。两次引导共发起 9 次模型请求，页面分批渲染时仍会触发额外观察。浏览器回归覆盖慢资源、高亮稳定性和详情延迟渲染。[实测 Issue #348483](https://github.com/microsoft/vscode/issues/348483)

README 引导在公开的 VS Code 仓库从首页找到文件，再高亮文件页的编辑菜单。独立浏览器未登录，展开菜单后只有 GitHub Desktop，扩展提示先登录。Fork 提示、已找到编辑入口和已经进入编辑器的区别，由本机浏览器回归验证。选择进入编辑器时，可以在 Fork 提示页看到下一步，切换到新副本后重新开始引导。[实测 README](https://github.com/microsoft/vscode/blob/main/README.md)

| 验证项 | 做法 | 记录什么 |
| --- | --- | --- |
| 实时指路 | 在 GitHub 找 README 编辑入口、打开指定 Issue，从仓库首页、文件页或其他中间页开始。 | 首次高亮是否正确，是否到达目标页面，哪一步选错。 |
| 页面变化后换路 | 在模拟页改动菜单层级或加入 Fork 提示，让用户自己点击。观察 AI 能否根据变化重新高亮或给出提示。真实 GitHub 上核对有写权限和无写权限时看到的不同状态。 | 是否能继续指路，是否识别权限分支，是否正确报告到达或卡住。 |
| 模型不可用或高亮建议失效 | 模拟模型不可用、页面已跳转或建议的控件已经消失。 | 侧栏说明暂时无法继续，用户可以重试。过期高亮及时清除。 |
| 换站点 | 在 Figma Design 练习稿打开后，引导用户从左侧 `Layers` 选中 `Frame 1`，再指出右侧布局区。已启用自动布局时显示 `Auto layout`，未启用时显示 `Layout`。也从图层已选中的状态试一次。 | 能否高亮图层、识别同一编辑器内的选中变化，并在两种布局状态下指出位置。 |
| 复用经验 | 在相同起点比较有经验和无经验的实时引导，再用一个相似起点看经验能否迁移。需要固定路线作对照时，单独运行旧版。 | 对比到达结果、误指次数、模型调用次数和等待时间。 |

首轮以跑通以上闭环并留下几条可复现记录为完成标志。实验之后再决定经验库能承担多少内容，以及是否需要作者工具。

2026-11-21，在 Edge 核对了 Figma 练习稿。未选图层时右侧显示 `Page`，选中 `Frame 1` 后出现 `Auto layout`。真实页面的图层行提供 `aria-selected`，右栏的 `Auto layout` 是可定位的标题。扩展根据当前选中状态提供引导候选，只读取这个任务需要的图层、布局标题和侧栏入口。设计稿名称和文件地址留在浏览器本地。[Figma 练习稿走查](../requirements/浏览器场景走查-2026-11-16.md)

真实试用还遇到 `Frame 1` 保持选中但处于 `Freeform` 的情况。Figma 将入口显示在普通 `Layout` 区域，旧版本只采集 `Auto layout` 标题，模型便误以为图层没显示。预设原型补齐了右栏标题观察。浏览器回归覆盖两种布局状态，以及选中其他图层时不会误指同名面板。

真实页面还把图层图标和名称都标成第 1 列。改为检查这一列的全部单元格后，在 Edge 的真实练习稿确认了两种起点。未选中时高亮 `Frame 1`，点击后改高亮右侧的 `Layout`。已经选中时直接高亮 `Layout`。

未启用自动布局时，扩展从右栏的透明复选框找到与它关联的可见图标，优先高亮实际开关。已在真实练习稿中确认高亮位置。找不到可见开关时仍可用 `Layout` 标题指示所在区域。

Figma 的这个任务以指出位置为完成条件。扩展确认目标已高亮后，侧栏显示「已找到自动布局」，网页中的高亮和气泡保留约 4 秒后自动收起。

### 查看原型的浏览器回归

原测试保留在 `codex/ai-navigation` 的 `tests/e2e/`。`sidepanel.spec.ts` 覆盖 Issue 和慢资源，`readme.spec.ts` 覆盖编辑菜单和 Fork，`adaptive.spec.ts` 覆盖页面变化与迟到响应，`figma.spec.ts` 覆盖图层、布局、高亮与收起。在仓库根目录可用 `git show codex/ai-navigation:tests/e2e/figma.spec.ts` 查看其中一个测试。
