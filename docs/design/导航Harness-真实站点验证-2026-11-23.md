2026-11-23。沿用初版 Harness `2ed28e5` 和本机同济模型配置。只测试导航、查看和筛选，不改仓库内容或 Figma 练习稿。[验收设计](WebGuideAI-导航-Harness-设计.md#8-怎样验证这套设计)

## 从验证中改了什么

- **入口未读到时先补看。** GitHub 首页确有 Activity 链接。通用模型指令现在要求先搜索用户点名而首读未带上的入口。用相同简化输入复跑两次，模型一次补看并选中 Activity，一次仍误选 Insights；浏览器回放另有一次成功补看并高亮 Activity。
- **现场拒绝指引后重读。** 选中 PR 合并后，页面加载中短暂仍显示 All activity。页面组件拒绝了迟到的旧高亮，但调度器仍把旧快照交给模型。现在核对失败就重读现场并清除旧补看记录，再进行下一次判断。新增回归验证第二次请求读到已生效的状态，并能完成引导。

修订后 `npm run check` 和本机 Chromium 回归均通过，共 57 项单元测试和 3 项浏览器测试。

## 网络恢复后的复测

- **同济模型 API**。直连和现有代理各探测一次，都收到 HTTP 403，响应提示当前网络环境受限。后续浏览器复测由本机模拟服务给出引导决定，扩展照常读取网页、验证控件和显示提示。
- **GitHub**。仓库首页和 Activity 页都能打开。两个起点各跑两次，4 次都将筛选切到 `Pull request merges`，页面显示筛选已生效，扩展也报告完成。首页起点各用了 10 次模拟判断，Activity 起点各用了 6 次。首次出现高亮约 0.2–0.6 秒，真实模型的等待时间待测。
- **Figma**。独立 Chromium 仍收到 HTTP 403，已登录的 Edge 能打开真实练习稿。用本机模拟服务，从已选中和未选中 `Frame 1` 两种状态各跑通一次。扩展能发现视口外的 `Add export settings` 按钮，提示滚动属性栏，看到按钮后确认完成，页面高亮和气泡自动收起。只查看了入口，练习稿内容没有改动。

Edge 复测发现了两个扩展问题。浏览器已授权时，侧栏偶尔没有收到打开网页的记录，现在可以从浏览器读回已授权的当前页。Figma 图层旁的锁定和可见性按钮在鼠标移开时消失，原先会改变图层名称并中断滚动引导。现在对象名称和行内操作分别采集，保留了对图层确实变更的识别。

类型检查、Lint 和生产构建通过，59 项单元测试与 4 项 Chromium 浏览器测试全部通过。

## DeepSeek Flash 真实模型复测

切换到 DeepSeek 官方 API 后，第一条虚构页面探针在约 2.8 秒内返回有效高亮指令。真实页面首次试跑使用模型默认推理强度，之后用 `reasoning_effort=none` 再测。下表是两批试次中完整返回的单次模型响应，未统计浏览器等待和操作时间。[DeepSeek 官方参数](https://api-docs.deepseek.com/api/create-chat-completion/)

| 本机设置 | 完整响应 | 单次响应中位数 | 输出截断 |
| --- | ---: | ---: | ---: |
| 默认推理强度 | 16 | 4.1 秒 | 1 |
| `none` | 36 | 1.3 秒 | 0 |

- **GitHub**。默认强度从仓库首页开始，两次都错选 `Insights`。从 Activity 开始的两次都完成了页面筛选，扩展没有给出完成确认。改用 `none` 后，两个起点各有两次可用试次。首页两次都先补看并找到 `Activity`，四次都实际选中了 `Pull request merges`，扩展均未报告完成。模型有时把筛选结果为空当成筛选未生效。两次打开网页时的连接断开已补跑。
- **Figma**。默认强度从已选中图层开始，扩展给出了正确的下滚方向，后续模型请求超时。改用 `none` 后，模型找到了 `Frame 1`，却在图层已选中时仍高亮左侧图层。追加一次明确点名 `Add export settings` 的试次，模型补看后正确高亮右侧加号，返回的仍是普通高亮指令，侧栏没有结束任务。测试只查看入口。

DeepSeek 的本机配置保留 `none`。下一轮优先验证两件事。首轮怎么提供与自然语言目标相关的控件，减少模型猜入口。收尾怎么说明哪些网页状态就足以满足当前任务，以及是否还需要用户操作。

## 同济恢复后的完成判定回放

同济 `DeepSeek-V4.1-Flash` 直连探针约 1.5 秒返回有效引导。随后用同一模型看十份合成页面状态及已有补看结果。现有方式给出最后一次引导决定；实验方式先从用户原话单独提炼终点，再判断同一批网页证据是否满足它。两边都在本地检查引用的编号和字段。样本根据真实问题构造，也加入了维基百科的文字大小选项。这轮没有模拟网页变化和实际高亮，也没有测用户等待时间。[维基百科外观选项](https://www.mediawiki.org/wiki/Reading/Web/Accessibility_for_reading/Updates/2024-06_deployments)

| 指标 | 现有方式 | 先明确终点 |
| --- | ---: | ---: |
| 已经完成的 4 个样本，判定通过本地复查 | 1 | 3 |
| 未达成或未证实的 6 个样本，错误收尾 | 1 | 1 |

- 提前明确终点后，两个容易混淆的例子得到了正确判定。GitHub 结果为空时仍能确认所选筛选已生效，Figma 正确图层的导出按钮可见时能建议收尾。找错图层、菜单选项还未选中、目标在视口外时继续引导。
- 两种方式都在网页仅显示「已导出为 PNG」时发出了能通过复查的完成决定，尽管用户还要核实文件已下载到电脑。网页提示只能证明导出这一步。现有方式有一次未返回可用引导，实验方式在维基百科已选 Large 时有一次返回空值，两者都按未收尾计。

下一版设计应让每个结果都有对应的证据来源。一项任务包含多个条件时，逐项核对已证实的部分和仍需确认的部分。入口高亮、页面内状态和页面外结果各用合适的证据。先补上这些区分，再用同一批样本和真实浏览器回归验证误报与漏报。

### 按证据来源逐项核对

第二轮用同济模型先从用户原话提炼条件，再在十五个合成页面状态上逐项找证据。模拟的用户确认单独交给会话，模型看不到这个输入。七种目标有六种首次返回可用条件。十五个样本中，十二个首次判对、一个漏判、两个缺可用回复，本轮没有误报完成。原型的四项本地检查通过。

- **导出与下载**。同一份「已导出 PNG」页面对不同目标给出不同结果。用户只要求核实网页显示时可以结束；用户还要求电脑上有文件时，实验会话保留待确认。网页即使写着「已下载到电脑」也不会生成用户确认。补入确认后可以结束；网页还在准备导出时，即便有下载确认也会继续核实导出。补测会议邀请时，网页只能确认邀请已发出，收件人的邮箱仍待确认。
- **入口和页面状态**。正确图层的可用导出入口能收尾，入口在视口外或图层选错时继续。实际进入 README 编辑器、维基百科文字大小已选 Large 时能收尾，遇到 Fork 提示或只看到 Large 选项时继续。
- **仍缺的线索**。GitHub 筛选摘要显示已选 PR 合并且列表为空时，模型首次没有给出证据，重跑返回了不可用回复。增加明确的「选项已勾选」状态后，该样本通过。两次结果说明还要验证页面怎样可靠地表达当前选择，单轮样本暂时不能说明模型为何漏判。

这轮用合成页面和程序模拟确认，不涉及网页跳转、绘制回执或侧栏交互。实验把条件提炼和结果核对分别调用了模型。接入时先试着用现有引导请求携带条件和证据，再测首条指引与收尾延迟。[试验设计](WebGuideAI-导航-Harness-设计.md#下一版试验设计)

## 引导循环接入后的复测

- **GitHub Activity**。打开真实练习仓库已应用 `Pull request merges` 的页面并展开筛选菜单。同济在一条引导回复里提供条件和「已勾选」证据。扩展复查后约 4.3 秒收尾，共一次模型请求。
- **Figma 导出入口**。已登录的 Edge 中，从选中 `Frame 1` 且导出控件在视口内的状态开始，输入「带我找到 Frame 1 的导出设置入口」。侧栏报告已完成，页面气泡已自动收起。测试只找入口，未点击加号。
- **下载确认**。真实同济用合成页面返回两个条件。Chromium 本机回归用可控制的模型回复，验证网页即便声称文件已下载，也仍需用户在侧栏确认。单元回归覆盖确认时网页证据过期、组合目标和多个入口，以及继续引导时恢复确认进度。

`npm run check` 通过，共 70 项单元测试。独立 Chromium 的 6 项浏览器回归通过。两个真实页面试次都从终点已可观察的状态开始。另一次用错误图层和同名按钮做的合成页面探针超时。接下来仍需从其他起点反复验证整条引导的成功率和延迟。

## 基线后的复测安排

先回放 F1 的两个相邻控件和 G1 的筛选生效状态，检验通用的入口证据与状态证据，同时记录上游响应和客户端取消原因。然后用相同四种起点复跑真实站点。每种起点至少有一次正确收尾且没有误报，再用第三个网站检验这套机制能否迁移。[验收设计](WebGuideAI-导航-Harness-设计.md#8-怎样验证这套设计)

## 收尾证据对照

从上表重建四份短观察，沿用同济模型和 9 秒时限。每份样本固定一项目标条件，旧版和新版分别请求三次。GitHub 记录引用了哪些字段，核对证明是否包含当前筛选值。结果统计模型提议，完整浏览器走查单独计数。

| 页面状态 | 旧版 | 新版 |
| --- | --- | --- |
| Figma 两个相邻控件都可见 | 2 次指对加号，1 次超时 | 3 次指对加号 |
| Figma 加号在视口外，标题可见 | 3 次误把标题当入口 | 2 次提示滚动，1 次输出截断 |
| GitHub 筛选生效，菜单已收起 | 3 次超时 | 3 次引用已生效的筛选值 |
| GitHub 只展开菜单，选项未选中 | 3 次继续引导 | 3 次继续引导 |

新版要求模型根据控件实际作用指路，并区分「可选项」和「当前值」。网页脚本原来只认可已选中、已勾选等状态，对收起控件的当前值会拒绝收尾。现在可复查收起控件上仍然可见且未变化的摘要。浏览器回归验证同一摘要在控件展开时不能单独证明完成。

### 放宽模型等待时间

当前先争取走通路线。扩展单次从 9 秒放宽到 15 秒，整轮从 20 秒放宽到 45 秒，本机服务从 12 秒放宽到 18 秒。模型配置、1,024 tokens 的输出上限和调用次数沿用上一轮，方便比较等待时间的影响。

用同济模型重放未选中图层、GitHub 首页和已筛选 Activity 三种短观察，各发两次请求。旧的 9 秒以内有 4 次通过服务校验，15 秒以内有 5 次。新增的一次是已筛选 Activity 的回复，约 9.6 秒返回。另一次 GitHub 首页请求在约 8.4 秒达到输出长度上限。这里衡量的是单次请求能否返回可用协议，真实页面的完整成功率仍需用原四种起点复测。

模拟时钟新增回归，两次各用 12 秒的请求能在同一轮先补看再绘制高亮。82 项单元测试、7 项 Chromium 浏览器测试均通过。

### 收尾证据里暴露的两个问题

- **过程被当成多个完成条件。** G4 筛选生效后，模型按「打开 Activity」「筛选成 PR 合并」「筛选生效」提交了三项证明。后两项引用了当前筛选摘要。第一项只引用仓库链接和 Activity 标题，这两种证据即使与现场相符，也无法单独通过当前的页面结果核对。扩展仍在等全部条件，正确筛选值无法使任务结束。
- **同一条件给了两个不同的高亮对象。** F2 的下一步指向 `Add export settings`，同一份回复却给第 0 项提交了两条入口证明。目标分别是正确的加号（编号 42）和选中的 `Frame 1` 行（编号 7）。会话按条件编号保存证明，后到的图层行覆盖了加号，浏览器因此把最后的蓝框画到图层行，同时侧栏报告完成。在浏览器里见到了错误的蓝框。

下一步先用这两份回复做可重复的用例。验收条件表达用户最后要看到的结果，把过程和上下文附在同一条件的证据里。每项入口结果只核对一个最终控件。遇到同时指向不同控件的证明，保留现场并复核冲突，再决定能否收尾。用重放和四种起点核对修改是否有效。
