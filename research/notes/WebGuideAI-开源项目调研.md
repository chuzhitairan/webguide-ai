# WebGuide AI：开源项目调研与实现建议

调研日期：2026-11-13。

本次下载了 9 个官方公开仓库的浅克隆，并针对与提案有关的核心路径做了第一轮静态阅读：教程生产、元素定位、引导推进、录制、状态验证和修复。没有安装项目依赖、启动服务、加载浏览器扩展或调用收费模型，因此下文的“已发现”表示源码或仓库文档中有相应机制，不表示本机已验证运行效果。所有具体版本及代码位置见 [源码阅读索引](./源码阅读索引.md) 和 [sources.json](../sources.json)。

## 1. 以主动复用为前提评估选题

本项目以完成软件工程课程设计、形成可运行的产品流程为目标，主动借鉴和复用已有功能。现成项目覆盖了 AI 生成步骤、按钮高亮、操作录制、元素等待和规则回退，这些都是降低实现难度的基础。评估时应关注复用后的集成成本、功能完成度和可靠性。原提案中“现有工具大多只是静态回放，一点偏就卡死”的表述仍应依据调研调整。

与提案最直接重合的是 **OnTheWay**。它已有页面 DOM 与用户意图生成步骤、可视化录制、Driver.js 引导、点击推进、跨页恢复和完成统计。**Usertour** 则提供更完整的用户引导平台结构，并已有元素与条件监测。**OpenAdapt** 的录制编译、确定性执行、异常时生成修复候选，也说明“正常流程快运行、异常时才用 Agent”并不是尚无人探索的架构。

这些现成能力为 WebGuide AI 提供了可借鉴的实现路线。建议工程目标是：**组合录制、教程生成、网页高亮、状态检查和 AI 纠偏，完成作者制作教程到新手实际使用的一条完整流程。**先在选定网站做好，再扩展适配范围。重合功能可以直接纳入项目，不需要为了差异化而回避。

按主动复用路线重新估算的难度、工期和优先级见 [实现难度与复用方案](./WebGuideAI-实现难度与复用方案.md)。

## 2. 九个项目分别学什么

| 项目 | 与提案的关系 | 源码中值得学习的内容 | 移植边界 |
| --- | --- | --- | --- |
| [OnTheWay](https://github.com/jiusanzhou/ontheway) | 最接近的功能对照 | 录制 → 标准步骤 → AI 文案/步骤生成 → SDK 引导；跨页进度 | 主要按网站接入 SDK 的形态设计；AI 生成不等于教程已经执行验证 |
| [Usertour](https://github.com/usertour/usertour) | 完整平台参照 | 编辑与发布、条件评估、元素查找/可见性监测、模块划分 | 平台范围大，第一版不宜整体复刻 |
| [Driver.js](https://github.com/kamranahmedse/driver.js) | 可优先验证的引导渲染组件 | 高亮气泡、用户事件推进、元素等待、目标移除后的重新绑定和规则回退 | 它不替你定义业务完成条件，也不会自动理解网站流程 |
| [Shepherd](https://github.com/shipshapecode/shepherd) | 另一种流程引导设计 | 声明式步骤、显示前异步准备、元素等待、条件跳过、JSON Schema | 有 AGPL/商业双许可；函数选项不能直接作为纯 JSON 下发 |
| [rrweb](https://github.com/rrweb-io/rrweb) | 录制与问题复现参考 | 全量快照与增量事件、页面重建、输入掩码和阻断区域 | 历史页面回放不能直接当成真实网站的任务教程 |
| [Nanobrowser](https://github.com/nanobrowser/nanobrowser) | 浏览器扩展与页面感知参考 | 页面表示、元素引用生命周期、结构化回执、动作前后证据 | 其 chrome.debugger/CDP 路线比普通内容脚本重；不必第一版全搬 |
| [Browser Use](https://github.com/browser-use/browser-use) | 自主 Agent 的对照 | 有预算的循环、超时、检查点、部分结果、完成状态与成功状态区分 | 当前 1.0 是持久 Python REPL 架构，不要按旧版 DOM 动作列表教程理解 |
| [Stagehand](https://github.com/browserbase/stagehand) | 页面理解服务的接口参考 | observe / act / extract 分离、结构化输入输出 | 当前 v4 SDK 的相关入口通过 RPC 转发；文档中的缓存是托管服务能力 |
| [OpenAdapt](https://github.com/OpenAdaptAI/OpenAdapt) | 示范学习和修复闭环参考 | 录制证据 → 工作流中间表示 → 后置条件检查 → 修复候选与版本演进 | 主体是自动执行系统，完整引擎很复杂；应借鉴契约和流程 |

## 3. 从源码学到的六件关键事情

### 3.1 一步教程不能只有 selector 和提示文字

OnTheWay 的 AI 接口接收 DOM 和意图，返回 element、popover、url、advanceOnClick 等字段。这足以表达“请看哪里、请点哪里”，但难以独立表达“操作完成后应当发生什么”。接口中的提示词要求引用真实 selector，但文本要求本身不构成页面上的验证。

OpenAdapt 的 Step 则将 intent、anchor、expect、effects 等内容分开。WebGuide AI 可以借鉴这个分工，设计一个更小的教程步骤契约：

```json
{
  "id": "open-project-form",
  "instruction": "点击“新建项目”，打开创建表单。",
  "page": { "origin": "https://demo.example", "path": "/projects" },
  "target": {
    "selectors": ["[data-testid='new-project']"],
    "role": "button",
    "accessibleName": "新建项目",
    "within": "项目列表工具栏"
  },
  "userAction": "click",
  "postconditions": [
    { "kind": "elementVisible", "selector": "[data-testid='project-form']" }
  ],
  "timeoutMs": 5000,
  "onFailure": "diagnose"
}
```

这是本项目的设计建议，尚未实现。第一版只支持少量可确定评估的条件即可，例如 URL 匹配、目标出现/消失、对话框可见、字段非空。不要让模型临时返回任意 JavaScript 当作完成条件。

来源：OnTheWay 的 AI 生成接口和实际 SDK；OpenAdapt 的 `ir.Step`，见[阅读索引](./源码阅读索引.md)。

### 3.2 定位需要同时保存长期特征和短期引用

Usertour 的定位结构并非只有一个 CSS selector，还容纳内容、顺序、自定义选择器和相邻节点等信息。Nanobrowser 则把运行期 ref 绑定到 session、frame、document、backend node，并在导航等情况下让引用失效。

对 WebGuide AI 的启发是区分两种数据：教程里保存跨会话可重用的目标特征；当前页面中保存本次实际解析出的元素引用。不要把某次页面里的 node ID 永久写进教程，也不要把录制坐标当作长期定位依据。

可以按“稳定属性 → 可访问角色与名称 → 所属表单/工具栏等上下文 → AI 提出候选”的顺序尝试。AI 的候选还要经过本地存在性、可见性、唯一性和上下文检查。若两个按钮都叫“保存”，仅凭名称不能确认目标；需要缩小到正确的对话框或表单。匹配分数和阈值需要用测试样本标定，不能预先宣称抗改版成功率。

### 3.3 普通偏离先用规则处理，AI 用于剩下的诊断

当前 Driver.js 的 `removal.ts` 已监测节点移除，尝试重新解析目标，并支持 stay、previous、previousAction 等处理；`wait.ts` 提供有超时的目标等待。Shepherd 也已有异步显示准备、元素等待和条件跳过。Usertour 的 watcher 则处理重试、可见性和 SPA 中目标重建。

因此，应先区分三种失败：

| 失败类型 | 例子 | 合理处理 |
| --- | --- | --- |
| 目标暂时不可用或定位变化 | 页面还在加载、节点重建、按钮文案调整 | 等待、重新定位、在候选中确认目标 |
| 用户偏离任务流程 | 关闭了必需弹窗、走入其他菜单 | 判断当前任务状态，提供回到已知状态的步骤 |
| 环境条件不满足 | 无权限、未登录、目标功能未开放 | 说明原因并暂停；不能靠换 selector 解决 |

第一版可把 AI 限定为返回“失败类别、候选目标、恢复步骤、依据”。恢复后重新检查当前步骤的前后置条件。只有定位变化不等于流程变化，更不等于任何改版都能自动恢复。

### 3.4 动作发生、页面变化和任务成功要分开

Nanobrowser 的 ActionReceipt 分别记录 dispatched、页面 effect 和 postcondition；Browser Use 的结果类型也区分运行结束和 Agent 自报成功。OpenAdapt 更进一步区分屏幕后置条件与 API/数据库读取确认的业务效果。

WebGuide AI 应相应地区分：用户点击了按钮；页面出现了表单；创建后的项目实际可见。点击只能证明动作发生，不能证明服务器接受了创建请求。

在第三方网页上，插件通常拿不到可信业务后台。第一版应清楚记录“页面证据通过”“用户确认”“尚未验证”等状态，而不是把成功气泡等同于数据库持久化成功。受控演示后台可以额外做一次独立只读查询，用来展示更强验证，但不能据此声称所有第三方网站都具备相同保证。

### 3.5 录制应当产出可编辑的步骤，而非原样事件流

rrweb 能保存页面快照和交互事件，用于在回放环境重建历史页面；OpenAdapt 的浏览器录制契约则保留有序动作、DOM 身份、几何信息和动作前后画面，供编译器进一步处理。两者说明，原始证据与任务描述是不同层次的数据。

建议 WebGuide AI 的录制输出包含：动作前状态、交互目标语义、动作类型、动作后变化、相对时间。随后去掉无意义的鼠标移动、合并连续输入，再让 AI 形成步骤草稿，由作者检查和发布。密码等字段只保留字段语义，不保存具体值；敏感信息处理应发生在采集和发送之前。

rrweb 的本次源码中，未显式配置时的输入掩码主要默认覆盖 password，并不是全部输入都默认隐藏。不能因为引入了录制库，就认为普通文本、邮箱和页面正文已经完成脱敏。

### 3.6 “持续进化”需要一个可审查的版本过程

OpenAdapt 的 self-repair 路径包含候选修复、探测、检查和批准，再进入新版本运行。具体机制比课程设计所需复杂，但它揭示了一个关键点：单次纠偏成功不能自动证明教程对所有人都应修改。

建议把反馈闭环实现为：失败事件聚合 → 定位失效或步骤缺漏的候选修改 → 在测试页面复现 → 管理者审阅 → 发布教程新版本。执行记录固定引用教程版本，避免一个用户运行到一半时被新版本悄悄改写。

## 4. 需要特别注意的源码版本差异

- **OnTheWay 有多套 SDK 文件。** `packages/sdk/src/index.ts` 已有点击推进、等待和跨页处理；`src/lib/sdk/index.ts` 与 `public/sdk.js` 的实现不同。分析和接入时应先确认实际使用的包入口，不能只读根 README 或旧文件就给项目下结论。本次核心判断以 `packages/sdk` 为主。
- **Browser Use 的当前架构已经变化。** 本次版本的 AGENTS 和实际代码均指向 Pydantic AI + 持久 Python REPL，并非旧版每轮直接从 DOM 中选一个动作。对本项目而言，运行预算与结果契约比整套执行器更值得学。
- **Stagehand v4 的接口不能等同于完整本地 AI 引擎。** 本次读取的 TypeScript SDK 将 act/observe 发送给 RPC 服务；v4 文档明确将缓存描述为 Browserbase 服务端能力，并说明本地浏览器不使用该缓存。不能根据老文章承诺“拿来就有离线缓存和全部推理实现”。
- **OpenAdapt 相关小仓库已出现迁移。** 本次下载的是主 monorepo，Flow 引擎位于 `packages/flow`，避免研究已经冻结的旧仓库后把旧结构当成当前实现。

## 5. 对 WebGuide AI 的具体实现建议

建议从 Driver.js 的渲染能力开始做小型验证，参考 OnTheWay 设计录制与编辑流程，参考 Usertour 设计条件检查和生命周期，再参考 Nanobrowser 与 OpenAdapt 设计证据和修复候选。平台、插件、AI 服务仍可分别开发，但共用一份版本化教程协议。

```text
教程作者录制 / 导入文档
        ↓
步骤草稿 → 编辑 → 在目标页面验证 → 发布固定版本
                                          ↓
用户选择任务 → 插件观察页面 → 本地定位 → 高亮说明
                               ↑              ↓
                          重新观察 ← 用户手动操作
                               ↓
                         检查完成条件
                    通过 ↙             ↘ 不通过
                 下一步骤           等待 / 规则恢复
                                        ↓
                                   AI 诊断与候选
                                        ↓
                              本地校验后继续 / 暂停
```

浏览器插件要在用户当前标签页就地观察，AI 诊断尽量接收过滤后的结构化页面状态。后端另开一个浏览器未必拥有用户相同的登录状态、权限、弹窗和表单内容，因此不能用后端重新打开同一 URL 代替对当前页面的判断。

跨页进度可以借鉴 OnTheWay，但第三方插件还需按 tab、origin、教程版本隔离状态；不能仅依赖某个网站的 sessionStorage 解决跨域和多标签页问题。第一版无需照搬 Nanobrowser 全套 debugger 控制层，可先验证内容脚本、侧边栏和页面消息之间的完整流程，遇到 iframe 等限制再具体扩展。

**推荐第一版边界：**一个受控管理后台、2～3 个完整任务、人工录制与编辑、明确的完成条件、页面高亮、跨页恢复、三类可复现偏离（走错菜单、关闭弹窗、目标文案/位置变化）、纠偏记录与教程版本。文档导入可以生成草稿；沙盒自主探索、多站点自动适配、开放教程市场放在扩展范围。

## 6. 怎样验证集成后的系统效果

验收重点是用户能否完成任务，以及发生偏离后能否恢复。下面的对照可以帮助判断状态检查和 AI 各自的作用，也可以按课程要求简化为功能测试与场景测试。

| 对照设置 | 用途 |
| --- | --- |
| 使用同一渲染库的固定步骤引导 | 测出基础体验；明确标注其启用的等待/回退等配置 |
| 固定步骤 + 业务完成条件与规则恢复 | 测出显式状态检查带来的贡献 |
| 上述方案 + AI 诊断恢复 | 测出 AI 在哪些偏离中有额外价值 |

对照场景可以固定为：正确操作、加载延迟、用户进入错误菜单、关闭弹窗、按钮文字变化、出现多个同名按钮、提交校验失败、权限不足。记录任务完成率、错误高亮次数、错误宣布完成次数、可恢复场景中的恢复率、恢复耗时，以及 AI 调用数/成本。

加载等待和规则回退是现成库已有的能力，对照中应合理启用，避免人为削弱基线。权限不足等不可恢复场景应统计是否正确暂停，不应混入“必须恢复成功”的分母。所有成功率和延迟在实际测量前都只是待验证目标。

## 7. 阅读顺序与复用建议

1. 先读 OnTheWay 的 `packages/sdk/src/index.ts` 与 AI 生成接口，搞清步骤从哪里来、怎样推进、何时被记为完成。
2. 再读 Driver.js 的 advance/wait/removal，明确现成渲染层已经解决哪些问题。
3. 读 Usertour 的 watcher 和 rules evaluator，将步骤推进与完成条件分离。
4. 读 Nanobrowser 的 refs、observation 与 ActionReceipt，设计当前页面的目标身份和证据格式。
5. 读 OpenAdapt 的 Step、编译入口和 self-repair，设计录制草稿与版本修复流程。
6. rrweb、Browser Use、Stagehand 按具体需求补读，不要为了架构看起来完整而全部接入。

许可信息已逐项目记录在索引与清单中。Driver.js、rrweb、Browser Use、Stagehand 的根许可为 MIT，Nanobrowser 为 Apache-2.0；Shepherd 的根文件声明 AGPL/商业双许可；Usertour 存在 enterprise/ee 和开关控制代码的例外；OpenAdapt 的 benchmark 和 third_party 有独立许可；OnTheWay 声明 MIT，但本次根目录未发现独立 LICENSE 文件。实际复用时应保留对应文件的来源和适用许可记录。

这些材料支持的结论是：基础能力已有很好的开源参照，应当积极复用。WebGuide AI 的主要工作在于将组件接入浏览器插件、统一教程协议、打通制作与使用流程，并验证状态检查和纠偏效果。
