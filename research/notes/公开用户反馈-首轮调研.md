# WebGuide AI：公开用户反馈首轮调研

检索日期：2026-11-13。背景：项目发起人本人是首位潜在用户，先通过公开讨论补充其他人的任务与问题，再结合本人操作记录、后续访谈和试用验证。

后续调研：2026-11-16 按项目发起人的意愿继续收集网络使用经历，新增 9 个 GitHub/Figma 讨论主题并复核本报告 U03、U04，见[GitHub 与 Figma 使用经历及需求线索](./GitHub与Figma-公开使用经历与需求线索.md)。个人回忆不再作为开始整理任务的前提。

## 1. 本轮能回答什么

本轮保留 5 个已打开原始页面的讨论主题，来自 Figma Forum、GitHub Community 和 Reddit 技术写作社区。可以核对发帖内容及部分回复，但未独立核实发帖者身份，也未亲自复现其中的问题。

这是一轮定向、探索性检索。它支持“这些问题确实被公开报告过”，帮助发现任务和需求假设；不能据此估计用户占比、市场规模、当前产品缺陷率或付费意愿。两个 Figma 主题与同一 UI 改版有关，不能当成两种独立市场趋势。一个帖子内的回复也不计作一位受访者。

大部分实例是历史报告，日期保留在下表；不能直接认定当下界面仍完全相同。Reddit 页面只显示相对时间，检索摘要与页面日期呈现不一致，发帖绝对日期暂未可靠核定。

## 2. 保留的原始讨论

### U01：新手发现教程与自己的网页界面不一致

- 来源：[Figma：HELP! Why is my design workspace missing elements?](https://forum.figma.com/ask-the-community-7/help-why-is-my-design-workspace-missing-elements-33728)
- 发帖日期：2024-09-02。
- 公开自述：发帖者表示刚开始学习 Figma，跟随多份教程，但教程的工作区与自己的界面不同，因此不知道该如何继续或改回相同设置。
- 回复信息：社区支持解释了当时 UI2 与 UI3 的差异。
- 可支持的问题：教程与当前界面版本不一致，会中断学习过程。
- 产品假设：引导需要识别当前界面上下文，并将同一个操作目标对应到不同版本的位置。
- 尚未证明：用户愿意安装扩展、允许读取页面或为该能力付费。

### U02：按视频执行具体步骤时，找不到 Variants 入口

- 来源：[Figma：Variants option missing from panel](https://forum.figma.com/ask-the-community-7/variants-option-missing-from-panel-15025)
- 发帖日期：2024-08-20；解决回复日期：2024-08-22。
- 公开自述：发帖者观看 Variants 教程并创建组件后，在属性面板中找不到教程所说的入口。
- 回复信息：被标记为解决方案的回复分别说明了两版 UI 的入口位置。
- 可支持的问题：用户有明确目标，却无法把教程步骤映射到当前控件。
- 产品假设：系统可以围绕操作意图展示当前可用入口，同时说明界面差异。
- 限制：与 U01 同属 Figma UI 改版背景，不把它单独计为另一条跨产品趋势，也不采用历史回复作为当前软件操作指南。

### U03：GitHub 评论仍是 Pending，用户误以为已经提交

- 来源：[GitHub Community：Make it clear that PENDING comments have to be submitted](https://github.com/orgs/community/discussions/10369)
- 原帖日期：2022-01-20；本次读到的后续自述包括 2026-09-18 的评论。
- 公开自述：原发帖者误解 Pending 状态，后来才发现评论并未发布，还需要提交 review。后续有人描述回复只有自己可见、协作者未收到的问题。
- 可支持的问题：点击或输入发生后，用户可能误判任务已经完成；缺少最后一步可能造成协作延迟。
- 产品假设：教程的完成条件应区分草稿、待提交和已提交；必要时引导用户找到最后一个提交动作。
- 限制：回复数量和投票不是用户总量；未核验每位回复者，也未在当前 GitHub 上复现所有状态。

### U04：提交 PR 并合并后，不知道怎样同步 fork

- 来源：[GitHub Community：Beginner warning: Next pull request after merge](https://github.com/orgs/community/discussions/156437)
- 发帖日期：2025-04-11。
- 公开自述：发帖者已完成多次 PR，但合并后看到 ahead/behind 和同步选项，不知道下一步如何处理，并担心再次破坏同步状态。
- 可支持的问题：用户需要根据当前状态解释下一步，而不是机械重复“创建 PR”的固定步骤。
- 产品假设：引导可以先判断用户处在哪个阶段，再给出适合的后续操作和解释。
- 限制：Git 的分支历史和本地仓库状态可能超出网页可见范围；单纯网页高亮未必能解决完整问题，不能宣称已找到确定根因。

### U05：文档作者难以维护随 UI 改变的截图

- 来源：[Reddit /r/technicalwriting：Let’s Talk Screenshots!](https://www.reddit.com/r/technicalwriting/comments/1xcn4l0/lets_talk_screenshots/)
- 发帖绝对日期：待核；本次已打开页面核对原帖和回复。
- 公开自述：发帖者询问截图维护经验。部分回复描述按钮位置或文字变化后需要重做图片、维护时间不足，以及大量版本和语言带来的负担。
- 不同意见：也有回复认为复杂软件离不开截图，文字与截图应互相补充，或主张改善产品本身的可用性。
- 可支持的问题：教程作者除了创建成本，还面对持续维护成本；引导工具需要考虑内容更新。
- 产品假设：记录教程适用版本、定位失效与修复候选；验证是否能减少作者的维护时间。
- 限制：它没有证明动态引导的总体维护成本一定更低，也没有形成对 WebGuide AI 的购买承诺。发言者的职业与经验均是其自述。

## 4. 由证据提出的需求假设

以下是我们的推断，尚不是已由用户确认的需求规格。

| 假设 | 线索 | 后续怎样验证 |
| --- | --- | --- |
| 对有明确任务却找不到入口的用户，就地引导可能有价值 | U01、U02 | 观察用户在目标网页完成任务，对比常规教程与引导的任务完成情况 |
| 教程必须检查真实的页面完成状态 | U03 | 设置“已输入但未提交”等情境，检验能否正确识别并避免错误宣布完成 |
| 应先判断当前阶段，再选择下一步 | U04 | 比较从不同初始页面/任务状态进入时的指引是否正确 |
| 教程维护者可能是独立于新手的重要用户 | U05 | 请实际维护者制作和更新一份教程，记录耗时与负担，而非只问是否喜欢这个想法 |
| 文字说明、截图和高亮需要按任务组合 | U05 的不同意见 | 实际比较理解、完成任务和维护成本，避免预先认定一种形式适合所有人 |

目前没有足够证据支持：普遍愿意付费、偏好全自动操作、愿意开放所有网站的读取权限、AI 学习教程能完全免去作者审核。这些应继续作为待验证事项。

## 5. 后续记录方式

继续收集时，每个主题记录：原始链接、发帖日期/版本、检索日期、任务目标、用户所处状态、卡点、后果、现有解决办法、是否已解决、来源是否有推广或组织关联、我们的推断与验证方式。

优先纳入具体求助、问题复现、使用后评价和有上下文的维护经验；同时检索无需工具也能解决的案例、对引导的负面评价和不适合网页操作的任务。按主题和同一改版事件去重，不把搜索结果数量当作用户规模。

项目发起人的经历另建为“种子用户使用记录”，与网络主题分开。之后由本人实际操作形成起始页面、目标、卡住步骤、尝试过程和耗时等证据，再选首个验证任务。

## 6. 与课程要求的关系

公开讨论研究可以用于调研报告的公开资料分析、问题证据和访谈问题设计；本人体验可以作为种子用户记录。它们与教师明确要求的真人干系人访谈是不同证据类型，不能改名写成已完成的访谈。后续真实访谈或试用观察应单独留纪要，并由团队确认需求。
