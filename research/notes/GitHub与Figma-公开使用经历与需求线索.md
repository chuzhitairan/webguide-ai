# GitHub 与 Figma：公开使用经历与需求线索

检索与整理日期：2026-11-16。用途：为 WebGuide AI 的第一阶段需求发现提供具体案例，减少对项目发起人回忆个人经历的依赖。

## 1. 本轮结论

本轮新增 9 个已打开原始页面的讨论主题，并复核首轮的 2 个 GitHub 主题。新增案例既包括 AI 帮助用户学习的正面经历，也包括 AI 指错入口、方案无法落地、模式切换导致控件消失、操作前提不满足、部署状态不明等问题。

最值得继续验证的产品假设是：用户带着具体任务求助时，把解释与当前页面、下一步操作、操作前提和结果检查结合起来，可能比单独提供一段操作说明更有效。该判断是我们的推断，还没有通过 WebGuide AI 原型比较得到验证。

这些资料足以建立第一批任务候选。它们没有证明付费意愿、扩展安装意愿、市场规模，也没有证明需要同时开发所有功能。项目的自动学习、专家录制、现场引导和教程维护仍是整体方向，本轮只补充它们需要服务的实际问题。

## 2. 检索与证据口径

- 主要来源：Figma Forum、GitHub Community、Reddit。优先直接阅读求助正文、作者补充和回复，排除仅有宣传或泛泛建议的材料。
- 主要检索词组合：`Figma ChatGPT help layout`、`Figma ChatGPT outdated`、`Figma auto layout confused`、`Figma prototype scroll greyed`、`GitHub Pages 404 help`、`GitHub settings permission can't find`、`GitHub ChatGPT beginner pull`。实际检索使用了站点限定及更多近义词。

- 9 指讨论主题数量，不是 9 次访谈、9 位独立验证过的用户或 9 种独立市场趋势。Figma 的 N03 与 N05 涉及同类模式差异，合并看待这一机制。
- 日期优先采用正文明确日期；Reddit 正文若仅返回相对时间，则单独说明搜索结果日期的核验限度。
- 所有案例均未亲自在当下产品中复现。历史界面位置不直接写入当前教程；“作者确认解决”“社区标记解决”“只有建议回复”“没有结果”分别记录。

## 3. 新增经历卡片

### N01：问了 ChatGPT，拿到布局规格，还是不知道如何在 Figma 中完成

- 来源：[Suggested Top Bar From ChatGPT](https://forum.figma.com/ask-the-community-7/suggested-top-bar-from-chatgpt-46637)，2025-10-24。
- 用户目标：按照 ChatGPT 给出的规格制作一个包含标志、项目选择器、搜索和头像的顶部工具栏。
- 已有条件与卡点：自述刚学 Figma，已完成外层 frame 的定义，随后不知道怎样创建和配置其中的子对象。帖子附有布局、尺寸、间距等 AI 输出。
- 现有办法与结果：从 ChatGPT 转而向 Figma 社区求助；本次打开的页面没有回复，未见完成结果。
- 可支持的事实：获得一份详细规格，不保证新手能把它转换为界面操作。
- 我们的需求假设：按对象创建和属性设置拆成可执行小步骤，结合当前选择给出下一步，并检查生成的结构和属性。不能直接假定帖子中的 AI 设计规格本身正确。

### N02：明确告知软件版本后，用户仍认为 AI 的操作指导反复出错

- 来源：[Horrible Figma instructions in ChatGPT](https://www.reddit.com/r/ChatGPT/comments/1oe2vil/horrible_figma_instructions_in_chatgpt/)。搜索结果标注 2025-10-23；打开页只显示相对时间，绝对日期未另行核验。
- 用户目标：使用 AI 帮助完成自动布局、组件、变量等 Figma 操作。
- 卡点与尝试：发帖者称，已经说明 Mac 桌面端和确切 Figma 版本，得到的步骤仍多次不对。
- 结果与限制：已读到的回复仅有版务机器人，没有可核对的完整 AI 对话、错误步骤或修复结果，不能确定错误成因，也不能据此判断当下模型表现。
- 我们的需求假设：下一步指令应与可见界面核对；用户反馈“不存在”后应重新检查上下文，避免不断重复同一路径。该帖子涉及桌面客户端，需求机制可参考，浏览器扩展不能直接覆盖其原生窗口。

### N03：以为更新删除了自动布局，实际是不知不觉切到了 Draw 模式

- 来源：[Update 125.5.6 — where are the auto layout options?](https://forum.figma.com/ask-the-community-7/update-125-5-6-where-are-the-auto-layout-options-42936)，2025-07-18；后续回复至 07-21。
- 用户目标：使用自动布局的对齐和方向选项。
- 卡点：工具选项消失，最初归因于软件更新。
- 解决过程：原作者随后说明自己试用绘图工具时切到了 Draw 模式，切回 Design 后选项恢复。其他回复也表示该办法帮助解决了问题。
- 证据状态：作者自报解决；我们没有复现。
- 我们的需求假设：找不到按钮时先识别当前模式，再选择适用的流程。它说明控件缺失可能来自状态差异，不能一律判断为网站改版或定位器失效。

### N04：想固定原型中的悬浮按钮，却只看到不可用的选项

- 来源：[Unable to apply Fixed position for floating button in prototype](https://forum.figma.com/report-a-problem-6/unable-to-apply-fixed-position-for-floating-button-in-prototype-option-is-greyed-out-without-explanation-40026)，2025-04-29；社区回复 05-02。
- 用户目标：设置悬浮按钮在滚动时保持固定。
- 卡点：选项灰显，界面没有说明原因，用户表达了挫败感。
- 回复信息：社区回复建议检查对象是否处于自动布局 frame 内，并说明当时相关对象需要满足绝对定位条件，附帮助文档。
- 证据状态：只有排查建议，未见原作者确认其文件结构或操作后结果。因此不能把回复推测写成已确定根因。
- 我们的需求假设：除了高亮控件，还要解释为什么不可用、检查必要条件并给出修正步骤；当前产品的准确规则需在正式教程中另行验证。

### N05：寻找绝对定位时，同时遇到模式与入口名称的差异

- 来源：[I cannot find the absolute positioning in the new update](https://forum.figma.com/ask-the-community-7/i-cannot-find-the-absolute-positioning-in-the-new-update-55388)，2026-06-28；相关回复 06-30 与 08-06。
- 用户目标：找到绝对定位功能。
- 可读到的信息：原帖主要为截图；本轮没有解析该截图中的全部内容。社区回复建议从 Draw 切回 Design，并说明 Position 区域中的 Ignore auto layout 入口。
- 证据状态：页面标记 Solved，相关回复标记为解决方案；未另见原作者详细描述最终操作。
- 我们的需求假设：可以用用户熟悉的目标词检索不同入口名称，再结合当前模式引导。
- 去重说明：与 N03 合起来支持“先判断模式”的机制，不把两帖算成两个独立需求类别。

### N06：HTML 已经上传，但不清楚 Pages 是否真的启用了

- 来源：[error in github pages，Discussion #200084](https://github.com/orgs/community/discussions/200084)，2026-06-25；建议回复 06-27。
- 用户目标：通过 GitHub Pages 发布网页；发帖者表示以前成功发布过其他站点。
- 当前状态与卡点：新建公开仓库，根目录 HTML 文件在仓库里能看见，但访问站点返回 404；Pages 发布分支显示 None，不确定问题来自配置、首页文件还是部署。
- 回复信息：有人建议启用正确的发布分支并检查首页文件名。
- 证据状态：搜索结果呈现过带 fixed 的标题和 Answered 状态，但直接打开页显示旧标题、Closed / Unanswered。本报告只认定“已有具体排查建议”，不据标题或标记冲突声称用户确认解决。
- 我们的需求假设：引导应串起文件存在、发布源已配置、部署结果和站点可访问这几个不同阶段；不能在文件上传后就宣布发布成功。

### N07：修改协作者权限，Copilot 却反复指向找不到的菜单

- 来源：[Can't edit permissions Collaborator，Discussion #154602](https://github.com/orgs/community/discussions/154602)，2025-03-21；回复 03-23。
- 用户目标：给已有协作者修改权限。
- 卡点与尝试：自述自己创建了账号与仓库，Copilot 一直让其去 Manage Access，但页面没有该入口，也没有期望中的齿轮或修改选项。
- 证据状态：有一条泛化建议回复，没有原作者确认解决；仓库归属类型、实际角色和完整 AI 对话都未核实，不能直接断言是权限不足或账号错误。
- 我们的需求假设：操作建议需区分仓库归属、当前角色和可用能力；用户指出菜单不存在时，应重新判断前提，必要时说明当前目标未必能通过这个界面实现。
- 答案质量提醒：不将该帖回复直接导入教程。本轮同时检索到官方个人仓库权限文档及一条声称文档与 API 行为不一致的 issue，未复现或裁定该争议。因此本案例只支持“AI 指引与实际界面不匹配”的使用经历，不提供确定的权限修复方案。

### N08：GitHub 新手不知从何开始；回复者描述截图问 AI 对自己有帮助

- 来源：[I'm totally lost on GitHub — where should a complete beginner start?](https://www.reddit.com/r/learnprogramming/comments/1kkrb3i/im_totally_lost_on_github_where_should_a_complete/)。搜索结果标注 2025-05-12；打开页只显示相对时间，绝对日期未另行核验。
- 原帖经历：新注册用户想协作和管理代码，却对分支、提交、仓库、PR 等术语感到不知所措，也不知道第一步该点哪里。
- 另一位回复者的经历：其表示自己在浏览网站卡住时截图给 ChatGPT，让它解释或帮助解决问题，认为这帮助建立了学习信心。
- 不同意见：其他回复主张先学习 Git 概念。这提示一部分困难来自概念和工作方式，单纯标出按钮不能解决全部问题。
- 证据状态：原帖和回复是不同人的自述；没有具体任务日志、耗时或完成率，不能宣称 AI 已替原作者解决问题。
- 我们的需求假设：支持围绕具体任务的即时解释与当前页面问答；先验证是否能省去用户反复描述或截图的负担，并保留必要的概念解释。

### N09：Pages 长期排队和 404，可能需要支持渠道，重复配置教程未必有效

- 来源：[GitHub Pages deployment stuck in Queue for 24+ hours and site returns 404，Discussion #198111](https://github.com/orgs/community/discussions/198111)，2026-06-05；被选中的答复 08-04。
- 用户目标：恢复之前能运行的站点。
- 已有尝试与卡点：自述已检查首页、发布源、公开可见性等，并重复提交和重跑任务，仍排队超过 24 小时；还看到账号被标记的提示，随后发现未登录时个人主页不可见。
- 回复信息：被原作者选中的答复将其判断为账号限制，建议通过支持渠道处理。
- 证据状态：有作者补充与选中答复，但未见恢复成功的完整记录；具体限制原因未经官方支持核实。
- 我们的需求假设：对于可能超出页面操作能力的问题，应提供有依据的诊断线索和退出路径。不能将“404”一律归入同一个固定配置教程，也不能承诺引导可以解除账号限制。

## 5. 从经历中提炼的待验证需求

以下是候选需求，不是用户已经批准的产品规格。优先级表示适合作为近期验证对象，不表示市场频率或承诺开发顺序。

| 编号 | 候选需求 | 证据依据 | 怎样检验它是否有用 |
| --- | --- | --- | --- |
| H01 | 根据当前模式、页面和对象选择，确定接下来可执行的步骤 | N03、N05、N07 | 从不同模式或起始页开始同一任务，检查能否正确识别差异，而非重复指向缺失控件 |
| H02 | 将任务或现成 AI 方案拆成实际可执行的小步骤 | N01；N08 为辅助线索 | 对比只给说明与现场引导，观察用户能否完成具体对象结构或网页任务 |
| H03 | 找不到入口或选项不可用时，先检查前提并解释原因 | N02、N04、N07 | 设置模式错误、选项灰显、权限未知的情境，观察系统是否核实而非编造入口 |
| H04 | 用真实结果检查进度和完成，区分中间状态与最终结果 | N06、U03 | 检验上传但未发布、评论仍是草稿等情境是否会被错误宣布完成 |
| H05 | 在具体操作前后补足必要概念，帮助选择下一步 | N08、U04 | 让用户解释为何选择当前动作，观察换一个起始状态后还能否做对 |
| H06 | 识别超出当前引导能力的阻塞，说明不确定性并转交支持 | N09、N07 | 遇到账号限制或未知权限时，检查是否停止无效重复并列出待核实信息 |
| H07 | 将重复求助点反馈给教程作者，支持更新与维护 | U03 的维护者回复；首轮 U05 | 让实际维护者处理一次教程失效，记录定位、修订和复核的工作量 |

没有案例直接验证：任意网站的 Agent 自主学习成功率、免审核发布教程的可靠性、自动修复的成本，或整个教程广场的需求强度。这些能力仍需独立验证，不能用上述求助帖替代技术实验或商业验证。

## 6. 第一批可验证任务候选

这是研究建议，任务步骤与当前界面规则尚未复现，也未确定最终开发范围。

| 候选任务 | 来自哪些经历 | 最终应核验什么 | 主要边界 |
| --- | --- | --- | --- |
| GitHub：发布一个简单 Pages 页面 | N06、N09 | 发布源、部署结果和目标站点内容；遇到外部阻塞时明确说明 | 需要自有练习仓库；配置成功不保证账号或服务正常 |
| GitHub：完成一次 PR review 评论提交 | U03 | 从草稿进入已提交状态，提交内容与目标 PR 对应 | 必须由用户确认公开提交内容；验证时用练习仓库与评论 |
| Figma：找回自动布局或绝对定位入口 | N03、N05 | 模式正确，目标操作在正确对象上可用 | 适合作为小型场景；两种入口问题共享部分前提 |
| Figma：配置滚动时固定的按钮 | N04 | 满足所需对象与布局条件，原型表现符合目标 | 要观察文件对象结构与原型结果，单靠网页高亮未必足够 |
| Figma：把工具栏文字方案落实为对象结构 | N01 | 子对象、层级与关键属性符合经过审核的方案 | 开放度与对象状态复杂；不要把 AI 原始规格当成已验证标准 |

我的建议：先拿 GitHub Pages 和 PR 评论提交作为端到端验证候选，Figma 的模式/入口问题作为第二组对照。理由是前两者任务终点较明确，便于在练习仓库形成可检查结果；并非认为 Figma 不重要。具体可行性仍要通过实际走查判断。

第一阶段的下一步可以直接由我们推进：核对候选任务的当前官方流程，在自有练习环境复现起始状态与成功/失败结果，再整理“谁在什么情况下，想完成什么，怎样判断完成”的用户故事。之后用真实用户试用比较普通说明与现场引导的效果。无需先让项目发起人补写回忆。

## 7. 使用限制与补充技术来源

本轮是公开讨论研究，支持发现问题与设计后续验证；不能写成已经完成教师要求的真人干系人访谈。所有来源都属于主动求助或参与讨论的选择性样本，英文社区占主要部分，不能外推国内学生或企业用户的比例。

未发现本轮保留帖明确披露推广自家同类产品，但这不等于独立身份认证。没有联系发帖者，没有发布求助帖，也没有收集私人资料。

为检查 N07 的建议质量，额外查看了以下检索材料，未将其计入使用经历：

- [GitHub Docs：个人仓库权限层级](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository)：本次返回的官方文档说明个人仓库 owner 与 collaborator 的权限模型。
- [github/docs #45537：声称个人仓库角色 API 行为与文档不同](https://github.com/github/docs/issues/45537)：仅作为待核实争议线索；本轮未打开核对完整 issue、未运行 API 实验，不据此推翻文档或给出当前技术结论。

后续研究仍应保留反面结果：有的问题用简短说明就能解决，有的问题属于产品缺陷、权限或账号状态，有的用户更需要学概念。WebGuide AI 的价值要通过实际任务完成与维护成本检验。
